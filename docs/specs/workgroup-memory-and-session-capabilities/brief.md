## Requirements

- Each workgroup has one canonical durable memory tree. Claude, Codex, OpenCode,
  and future sibling providers in that workgroup read and edit the same memory.
- Agent-group identity, instructions, provider configuration, credentials, and
  provider continuation state remain separate. Sharing memory does not collapse
  sibling agents into one agent.
- Before every ordinary provider response, NanoClaw automatically supplies
  relevant canonical memory and relevant conversation history, preferring the
  current thread. This applies to first wake, warm continuations, compaction,
  rotation, and replacement continuations.
- The automatic recall path reads authoritative sources directly. Graphify may
  help, but a stale, empty, or unavailable derived index cannot erase canonical
  memory or same-thread history.
- Before the first response and on later turns, the provider receives the
  current session-scoped capability state without needing to discover and call
  an optional tool. If an access path is available, the provider must use or
  verify it before claiming the service or linked content is inaccessible.
- Existing conversation archives remain durable exact provenance and a recall
  source. They do not become a second canonical distilled-memory tree.
- Existing direct Markdown memory behavior remains available to agents. Durable
  distilled memory is curated in the shared tree rather than generated by a
  mandatory semantic classifier.
- Migration discovers every legacy memory source at execution time, accounts
  for every byte, preserves distinct content and collisions, records checksums,
  retains a permanent rollback copy, and changes sibling paths only after
  verification.
- The behavior and migration contract cover every sibling provider, not only
  Claude or only the currently non-empty stores.
- The memory and update skills for both Claude and Codex document and enforce
  the same full-merge, customization-first, audit, migration, and rollback
  contract.

## Constraints

- [HARD] User customizations and existing durable memory take precedence over
  upstream defaults. Unknown or conflicting content is preserved, never silently
  discarded or overwritten.
- [HARD] One canonical read/write memory tree exists per workgroup; sibling
  agent groups do not own independent authoritative copies.
- [HARD] Unrelated workgroups remain isolated. Trusted host workgroup membership,
  not model-supplied paths or identifiers, defines the recall boundary.
- [HARD] Existing session-specific owner-safety filtering for credentials and
  capabilities remains intact.
- [HARD] Recalled Markdown and archived messages are delimited reference data,
  not trusted instructions or executable host actions.
- [HARD] Migration is deterministic, auditable, collision-safe, reversible, and
  does not delete rollback material automatically.
- [HARD] Provider-specific standing instructions, configuration, state, and all
  non-memory workgroup customizations remain byte- and behavior-preserved.
- [SOFT] Prefer the smallest architecture that reuses current workgroup storage,
  archive, capability, and session-message seams. A new subsystem requires proof
  that an existing seam cannot satisfy a requirement.
- [SOFT] Keep injected context bounded and relevant rather than loading the full
  memory tree or archive on every turn.

## Non-Goals (Explicitly Out of Scope)

- Automatically classifying every message into a second durable fact store.
- Adding a general principal/conversation audience policy language inside a
  workgroup; the existing workgroup data-pool boundary remains the sharing model.
- Making Graphify authoritative or redesigning Graphify authorization.
- Rebuilding container admission, spawn accounting, delivery idempotency,
  credential lifecycle, workspace mounts, or Git promotion.
- Adding a new memory database, coordinator, revision ledger, release-view
  system, per-turn isolated container, or cross-channel declassification system.
- Restoring provider-native opaque memory as another source of truth.

## Key Concepts

- **Workgroup:** The intentional shared-data boundary above sibling agent groups;
  siblings share memory, archives, files, Graphify, and declared secret baseline.
- **Canonical memory:** The single shared Markdown tree containing curated,
  provider-portable durable memory for one workgroup.
- **Conversation archive:** Exact historical messages with provenance, searched
  for relevant context but not treated as curated canonical memory.
- **Pre-turn context:** Bounded memory, conversation, and capability context
  supplied by NanoClaw before a provider answers.
- **Compatibility path:** The provider-facing memory path retained so existing
  agents and customizations continue to work while pointing at workgroup canon.

## Open Questions

None. The user chose one workgroup canon, customization-first migration, and the
simple existing-seam architecture. Remaining choices are implementation details.

## Success Criteria

- In the referenced SipTrue Discord thread, a provider receives the prior
  same-thread fact that DNS is managed in Wix before answering.
- A pasted Slack or Discord URL does not produce a false blanket denial when
  the session has an available archive or API access path.
- A Madison Reed sibling receives the known Snowflake-backed GSC access path and
  does not default to an unavailable Workspace API.
- A memory edit by one sibling is visible to another sibling in the same
  workgroup on its next turn, while a different workgroup cannot retrieve it.
- Claude, Codex, and OpenCode pass the same first-wake, warm-turn, rotation,
  capability, sibling-memory, and cross-workgroup isolation fixtures.
- Migration reports every discovered source and checksum, ignores only the exact
  known empty scaffold, preserves all distinct and colliding bytes, and proves a
  rollback copy before compatibility paths change.
- The implementation introduces no new central DB schema or runtime transport
  and does not alter unrelated workgroup, credential, workspace, or delivery
  behavior.
