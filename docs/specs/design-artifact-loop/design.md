# Design: Design Artifact Loop

> Generated by `/team-design` — 2026-06-24
> Saved to: `docs/specs/design-artifact-loop/design.md`

## Brief Reference

Make nanoclaw agents (claude/codex/opencode) produce non-slop, render-grounded UI
designs delivered through chat. Mechanism (validated by two Codex passes + a live
two-render experiment): **author-then-conform** (commit a concrete DESIGN.md before
markup) + **render-grounded iteration** (render → screenshot → critique → revise) +
a **separate, genuinely-independent critic** + **must-fix carry-forward** against a
**concrete artifact contract**, in a **bounded** loop, delivered as chat-ready HTML +
preview image. Do NOT integrate Open Design's daemon. Full brief:
`docs/specs/design-artifact-loop/brief.md`.

- **C1 (parity) is the live risk, not C2.** Research (below) shows the *render* step
  is already at parity, but **skill discovery is auto only for Claude** — Codex and

## Options

### Option A: Pure instruction-only skill (SKILL.md + bundled scripts)

**Approach:** A mounted `container/skills/<name>/` containing SKILL.md + vendored
design-systems (curated subset + index) + a bundled deterministic linter script. The
SKILL.md instructs the agent through the whole loop; the agent calls `agent-browser`
and the linter via Bash, and `send_file` to deliver. No host/runner code.

**Pros:**
- Maximally parity-clean — pure files; rides the existing skill mount.
- Lowest build cost; no agent-runner changes.

**Cons:**
- The loop is **prompt-enforced only** — the deterministic gate and must-fix
  carry-forward are "please run the script," which the model can skip. This is exactly
  Codex's "ritual theater" failure mode (brief review §6).
- No structured trace guaranteed (R9/SC4 want observable cap state).

**Pattern alignment:** Matches CLAUDE.md "Skills" (mounted files).
**Confidence:** Medium — works, but weak on enforcement (the whole point per Codex).
**Assumptions:** Agents reliably self-run the gate every round.

---

### Option B: Skill + a focused MCP tool for render + deterministic critique *(recommended)*

**Approach:** Mounted skill (SKILL.md + vendored design-systems + index) drives
author-then-conform and the round structure. A **new MCP tool**
`design_review` (in `container/agent-runner/src/mcp-tools/`, provider-agnostic like
`send_file`) takes an HTML path + DESIGN.md + round state and **deterministically**:
renders via chromium/agent-browser, runs the bundled linter (contract + branded-generic
mechanical checks), and returns a structured result `{screenshotPath, findings[],
mustFixOpen[], round, status}`. The **taste critic** (R5) is a fresh-context critic
pass given only `{screenshot, DESIGN.md, rubric}` — not the generation transcript. The
tool maintains the must-fix list across rounds (carry-forward) and enforces the cap +
R9 gate. Final delivery via `send_file` (HTML + PNG + trace).

**Pros:**
- The deterministic gate **always runs** with structured output — kills the theater
  risk and makes R6/R9/SC4 observable.
- Provider-agnostic by construction (MCP tools are shared — `send_file` precedent),
  so C1 parity holds for the loop machinery.
- Reuses chromium/agent-browser (C2) and send_file (R7); no new external service (C6).

**Cons:**
- Adds agent-runner code (bind-mounted, deploys on respawn — moderate build).
- The taste-critic independence still relies on a fresh-context pass (see Assumption A2).

**Pattern alignment:** CLAUDE.md "Container Runtime" (MCP tools in agent-runner,
shared across providers); `send_file` is the provider-agnostic precedent.
**Confidence:** High for render/linter/delivery (verified); Medium for the
fresh-critic independence mechanism (A2).
**Assumptions:** A1 (skill mirrors to all providers), A2 (fresh-context critic is
spawnable parity-clean), A3 (linter checks are meaningful, not noise).

---

### Option C: Skill + full in-runner convergence controller

**Approach:** An MCP tool that internally drives the entire generate→render→critique→
revise loop with a scoreboard, calling back to the agent for generation/critique —
essentially re-implementing Open Design's daemon orchestration inside the runner.

**Pros:** Strongest loop discipline; cap/scoreboard fully code-enforced.
**Cons:** Heavy; re-creates the daemon-in-orchestrator pattern we explicitly rejected
(NG1 spirit) one level down; fights nanoclaw's "agent is the planner" model; high build
cost; over-engineered for v0.
**Pattern alignment:** Weakest — inverts the planner model.
**Confidence:** Low for v0 value/cost ratio.
**Assumptions:** Worth re-building daemon-grade orchestration in-runner (we decided not).

## Recommendation

**Selected: Option B** — mounted skill + a focused `design_review` MCP tool, with a
fresh-context taste critic.

**Justification:** It directly operationalizes Codex's verdict — *"render-grounded
iteration with explicit must-fix carry-forward and a concrete artifact contract"* —
with **enforced execution** rather than prompt-hope (Option A's fatal weakness, and the
exact theater risk Codex flagged). It satisfies C1 parity structurally (MCP tools are
shared across providers, per the `send_file` precedent) and C2/R7 by reuse (verified),
without the over-engineering of Option C or the daemon we rejected (NG1). The
deterministic linter replaces the host-only `impeccable` cleanly and runs in-container
for all three providers.

**Confidence note:** High on the verified machinery (render, linter, delivery, single
image). Medium on two parity points the build must prove FIRST via the mandatory
pre-implementation spike: (A3) a new `container/skills/` dir surfacing to Codex *and*
OpenCode AND `design_review` being invocable there, and (A4) an **L1** critic
(separate process, screenshot-ingesting) being spawnable on all three. Note the honest
calibration (per Codex review): the v0 taste critic is **L1 — separate-process,
same-provider, reduced-independence** — NOT "genuinely independent" in the cross-model
sense (that is L2, deferred). The spike is a hard gate; a provider that can only do L0
self-review fails parity for v0.

### Concrete specifications

**Artifact contract (R3) — a valid artifact MUST:**
1. Be a **single self-contained HTML file** (C8): CSS inline/in `<style>`; fonts via a
   documented CDN link **with a Georgia/system-ui fallback chain**; **no external
   `<script>`** and no network calls beyond the declared font CDN unless explicitly
   disclosed; no embedded credentials/session/internal data.
2. **Bind to a named DESIGN.md via a machine-checkable token trace** (R1/R2): the
   artifact MUST declare a `:root { --token: value }` block whose tokens are lifted
   from the chosen DESIGN.md (`tokens.css`), and all color/type/space/radius/shadow
   usage MUST reference those custom properties (`var(--token)`). The linter flags raw
   hex/`rgb()`/px values used outside the `:root` block beyond a small allowlist
   (e.g. `0`, `1px` borders, `100%`). This replaces heuristic "traces to tokens" with
   an enforceable check (no separate manifest needed — the `:root` block IS the trace).
3. **Cover required states**: any interactive/data surface includes at least empty +
   populated; data views also loading + error.
4. **Be responsive** at the pinned viewports (below) with no overflow/broken layout.
5. **Meet a11y basics**: WCAG AA text contrast, semantic landmarks, visible focus.
6. **Render successfully**: agent-browser/chromium produces a non-blank PNG at each
   pinned viewport.

**Render environment (C2), pinned with exact commands + thresholds:**
- Engine = system chromium (`/usr/bin/chromium`, image-pinned). Primary command:
  `agent-browser screenshot <file|url> --output <png> --viewport <WxH>`; fallback:
  the `render-diagram` MCP chromium path (`chromium --headless --screenshot=<png>
  --window-size=<W,H> <file>`). The MCP tool, not the agent, issues these.
- Viewports = **1440×900 (desktop)** and **390×844 (mobile)** — both rendered every round.
- **Blank/failure threshold:** render is a **must-fix (severity high)** if the
  command exits non-zero, OR the PNG is < 2 KB, OR > 98% of sampled pixels are a single
  color (blank/whiteout). **Overflow check:** must-fix (high) if
  `document.documentElement.scrollWidth > viewport width + 2px` at either viewport
  (horizontal overflow), measured via the headless page before screenshot.
- **Assets / font-CDN semantics (C8, F6):** the artifact must render acceptably with its
  fonts' fallback chain when offline. Note (Reviewer A F6): under
  `NANOCLAW_EGRESS_LOCKDOWN` the container has no internet route except the OneCLI
  gateway and the chromium screenshot args set no `--proxy-server` — so a font CDN
  simply will not load at render time and the **fallback always renders**. Treat CDN
  fonts as a delivery-time nicety, not a render-time dependency; a hard dependency where
  layout breaks without the CDN IS a must-fix (high).
- **No-JS v0 policy + network-construct lockdown (C8, F8; Codex cycle-4 should-fix):**
  v0 artifacts are **static HTML/CSS only — NO JavaScript**. The linter flags ANY
  `<script>` (inline OR external) as **high severity**, plus any other network-capable
  construct (`fetch`, `XMLHttpRequest`, `<img src="http…">`, `<link rel="preconnect">`
  beyond the declared font host). This removes the "is this inline script harmless?"
  debate at build time and closes the inline-beacon exfil vector. (A later phase may add
  a narrow opt-in safe-script policy; not v0.)
- Screenshot format = PNG. Trace + both PNGs + HTML stored under
  `/workspace/agent/design-artifact-loop/<id>/` (persistent, send_file-able).

**Branded-generic rubric (SC3):** define the **"slop baseline skeleton"** =
{top-nav + centered hero w/ gradient + 3 equal feature cards + generic left sidebar +
plain unstyled table}. The rubric (run by the linter where mechanical, by the taste
critic where judgmental) requires: (a) layout structure differs from the slop baseline
with choices justified by the DESIGN.md/product; (b) typeface not in the AI-tell
denylist {Inter, Roboto, Space Grotesk, Geist, Plus Jakarta Sans, Fraunces} unless the
DESIGN.md justifies it; (c) every value traces to DESIGN.md tokens; (d) the design
commits to the system's distinctive moves (e.g., ring vs drop shadows). Ship a small
**fixture set** (kanban board, settings page, pricing page) each with its slop-baseline
render, used as the SC3 acceptance harness.

**Independent critic (R5) — with explicit independence levels.** Two layers; the taste
critic's independence is graded honestly (per Codex design review — same-model
reduced-context review is NOT "genuine independence"):

1. **Deterministic linter** (bundled Node/Bun script, Cheerio-style HTML parse — the
   in-container replacement for the host-only impeccable): mechanical contract + rubric
   checks (self-contained, font denylist, token-trace via the `:root` rule above,
   presence of states, contrast where computable, render-success, overflow). Emits
   `{id, severity, locus, message}` findings. This layer IS truly independent of
   generation (deterministic code) and is the enforceable gate.
2. **Taste critic** (judgment) — independence levels:
   - **L0 — same-turn self-review:** the generating turn critiques itself. **NOT
     permitted as the R5 critic** (it is not independent; it is the theater risk).
   - **L1 — separate sub-agent/process, same provider, screenshot-grounded
     (v0 BAR):** a critic spawned as a distinct sub-agent/process that receives ONLY
     `{screenshot PNG, DESIGN.md, rubric}` — never the generation transcript — and MUST
     demonstrably ingest the PNG (vision). This is "reduced-independence, separate
     process," explicitly labeled as such — better than L0, weaker than L2.
     **Reviewer A F4 caveats (do NOT assert L1 works on all three until the spike
     proves it):** (a) **vision ingestion is unproven** — the inbound formatter passes
     images to the model as TEXT references (`[image: … saved to …]`,
     `formatter.ts:480-493`), not vision content blocks; the critic only "sees" pixels
     via a provider/tool-specific vision read, which the spike MUST demonstrate per
     provider. (b) **OpenCode has no present same-provider subagent spawn primitive**
     (`opencode.ts:131-135` calls it "future"); its viable cross-process critic is
     **`codex exec --yolo`** (a different model = L2). So on OpenCode, L1-same-provider
     may be unattainable — the spike decides whether OpenCode uses `codex exec` (L2,
     which would be a documented per-provider exception) or fails v0 for that provider.
     Name `codex exec --yolo` as the concrete cross-process critic invocation.
   - **L2 — cross-model critic:** a different provider judges. Strongest; **deferred
     (NG/v0-out)**.
   - **v0 requires at least L1.** If a provider cannot spawn an L1 critic that ingests
     the screenshot, that provider does NOT meet R5 and the parity spike fails for it
     (no silent downgrade to L0).

**Trace & severity schema (R9) — explicit, so QA is deterministic:**
- **Finding identity:** each finding has a stable `id` = `<check-key>:<locus>` where
  `check-key` is the rule (e.g. `font-denylist`, `overflow`, `state-missing`,
  `taste-branded-generic`) and `locus` is a stable HTML locus (selector path or
  `viewport` for render-level). Same `id` across rounds = the same finding (enables
  carry-forward); a finding absent in a later round = **resolved**; still present =
  **unresolved**; a new `id` = **new**.
- **Severity taxonomy (fixed, not reviewer taste):**
  - **high** = contract violation that blocks ship: render fail/blank, horizontal
    overflow, external script / network egress beyond declared font CDN, credential/data
    leakage, WCAG-AA text-contrast failure, missing required state on a primary surface,
    raw non-token color/type values outside the `:root` allowlist.
  - **medium** = quality/branded-generic issues: AI-tell font (unjustified), layout
    matches the slop-baseline skeleton, weak hierarchy, missing non-primary state.
  - **low** = polish nits.
- **State store (Reviewer A F1/F2) — disk, not memory, not outbox:** round/cap state and
  the trace MUST be rehydrated from a disk file on **every** `design_review` call
  (read-modify-write), NOT held in MCP-tool module memory — on Codex the app-server (and
  its child `nanoclaw` MCP process) is spawned and torn down per query
  (`codex.ts:731-736,978-982`), which would reset in-memory `{round,findings[]}` mid-loop
  and break C1 parity + R6 carry-forward on Codex. The authoritative store lives under
  **`/workspace/agent/`** (the agent's private *persistent* dir AND a valid `send_file`
  source) — NOT `/workspace/outbox/<id>/`, which is host-owned, deleted after delivery
  (`session-manager.ts:772`) and absent from `send_file`'s source allowlist
  (`core.ts:23-29`). Artifacts/PNGs/`trace.json` are authored + iterated under
  `/workspace/agent/design-artifact-loop/<id>/`; the delivery tool stages into
  `outbox/<id>/` internally only at send time (the `render_diagram` pattern).
- **Concurrency + durability (Codex cycle-4 must-fix):** the read-modify-write on
  `trace.json` MUST be **atomic** — write to a temp file in the same dir then `rename()`
  (atomic on the same filesystem), guarded by an advisory lock (e.g. a `trace.lock`
  lockfile or `flock`) so overlapping `design_review` calls on the same `<id>` cannot
  lose findings or corrupt the trace. **Crash recovery:** if a call finds rendered PNGs
  newer than the last `trace.json` write (process died mid-round), it reconciles by
  treating those PNGs as the in-progress round's render and re-running the critic step
  for that round rather than trusting partial state — the trace is authoritative; orphan
  PNGs without a corresponding trace round are discarded.
- **Round/cap state machine:** `design_review` reads `{round, findings[], status}` from
  the disk store each call. Cap = 3 (OQ5). After each round the agent revises against
  `unresolved`. At cap:
  - any unresolved **high** → `status: blocked` (NOT delivered as final; returns the
    unresolved-high list for the agent to either fix in one allowed overflow round or
    surface to the user).
  - else (only medium/low unresolved) → `status: shipped-with-disclosures`; the
    unresolved findings are written into the delivered trace.
- **Trace artifact:** `/workspace/agent/design-artifact-loop/<id>/trace.json` =
  `{rounds:[{round, findings:[{id,severity,locus,message,state}]}], finalStatus,
  selectedCandidate}` — persistent + send_file-able; staged into outbox at delivery and
  referenced in the chat message.

**Vendoring (OQ1/C4/C5):** vendor ~15–20 app/product-oriented Open Design design
systems (`design-systems/<name>/{DESIGN.md,tokens.css}`) + an `index.md` (name +
one-line vibe + use-case) into the skill dir, read on demand (never eager-loaded). Carry
Open Design's Apache-2.0 LICENSE + attribution in the skill dir.

### Pre-implementation parity spike (MANDATORY gate — must pass before full build)

Per Codex design review (Q7): before implementing the full skill, run an executable
spike that converts the two weakest claims (A3 skill-mirroring, A4/R5 critic
independence) from prose into proof. For **each** of claude, codex, opencode:

1. Mount a minimal stub skill + a stub `design_review` tool; confirm the provider can
   **discover the skill AND invoke `design_review`** (not just see the SKILL.md).
2. Run `design_review` on **one fixed bad fixture** (the slop-baseline kanban) and
   **one fixed good fixture** (this session's "Signal" render) → require deterministic
   structured findings (bad fixture flags ≥1 high/medium; good fixture passes).
3. Spawn the **L1 fresh critic**, pass it the **screenshot PNG**, and **PROVE vision
   ingestion** using an explicit **pixel-only sentinel fixture** (Codex cycle-4
   should-fix): a fixture HTML whose distinguishing detail is determinable ONLY by
   rendering — e.g. a colored marker box positioned by computed layout, or text whose
   final on-screen color comes from CSS cascade/overlap that cannot be read off the
   source — and the critic is NOT given the HTML source, only the PNG + rubric. The
   critic must report that sentinel detail to pass (Reviewer A F4: images arrive as text
   refs by default, so this is the single most load-bearing unknown). Then require a
   correct `blocked` vs `shipped-with-disclosures` status. On OpenCode specifically, also determine whether a
   same-provider L1 critic is spawnable at all, or whether `codex exec --yolo` (L2) is
   the only cross-process option.

**The spike FAILS for a provider if:** the skill/tool isn't invocable, the critic cannot
**prove** it ingested the screenshot, or the critic only runs as L0 same-turn
self-review. A failing provider blocks v0 for that provider (parity, C1) until wired
(skill mirror) or an explicit documented fallback (e.g. OpenCode→`codex exec` L2) is
defined — it must NOT be silently downgraded. This is the first /team-build task and a
hard gate on the rest of the build.

## Step 6c — MVP Scope Boundary

**Scope resolution (Reviewer A F5, cycle 3):** the overlapping upstream skill
`container/skills/frontend-engineer` (gavrielc, Apr 2026 boilerplate — a Vercel
build-and-deploy skill, not authored by the operator and explicitly unwanted) has been
**removed** from the tree. design-artifact-loop is built **standalone** with no
reconciliation needed — there is no longer an overlapping render-verify loop mounted.

**IN (v0):** mounted skill + `design_review` MCP tool (render + deterministic linter +
structured findings + carry-forward + cap/R9; **disk-backed state under
`/workspace/agent/`**); L1 fresh-context taste critic (vision-proven by the spike);
~15–20 vendored systems + index; artifact contract; branded-generic rubric + 3-fixture
acceptance harness; chat delivery via send_file; cross-provider skill surfacing + the
mandatory parity spike.

**OUT (deferred, one-line rationale):**
- Cross-model critic (different provider judging) — v0 uses fresh-context same-provider
  critic; cross-model is a quality add-on.
- Exports PPTX/MP4/PDF (NG2) — demand-gated escape hatch.
- Persistent design memory (NG4) — product-memory semantics beyond v0.
- Daemon/MCP integration (NG1), Electron app (NG3) — settled rejections.
- Authoring brand-new systems from a URL/screenshot import — v0 authors from
  brief/curated systems; import is later.
