# Brief: Design Artifact Loop

> Generated by `/team-brief` — 2026-06-24
> Saved to: `docs/specs/design-artifact-loop/brief.md`

## Background / Problem

When asked to design an app, site, dashboard, or other UI, nanoclaw agents
(Claude / Codex / OpenCode) produce generic "AI slop" — the statistical average
of web UIs (default component kits, generic palettes, the same hero/cards/sidebar
skeleton). The operator tried the existing design-**critic** plugins (`impeccable`,
`taste-skill`) and found the output still looks AI-generated.

Investigation this session established the root cause and the fix:

- **Root cause:** slop is the absence of a *committed* design system. Critic skills
  only flag known tells after the fact; they do not make the agent commit to a
  coherent set of design decisions up front.
- **Fix (validated by two independent Codex review passes + a live two-render
  experiment):** "author-then-conform" — the agent commits to a concrete design
  system *before* writing markup — combined with **render-grounded iteration**
  (render → screenshot → critique → revise) and a **separate critic pass** with
  **explicit must-fix carry-forward** against a **concrete artifact contract**.

The decision NOT to integrate the Open Design daemon (the OSS Claude Design clone)
is settled and recorded as a non-goal below: the daemon has no model of its own —
it spawns the host's agent CLI — so integrating it would be an orchestrator inside
an orchestrator, would break the cross-provider parity rule ("provider laundering"),
and would mismatch nanoclaw's secret/auth model. We port the *mechanism*, not the
daemon.

## Requirements

- R1. An agent that is asked to produce a UI design MUST commit to a concrete,
  named design system (palette with semantic roles, type pairing, depth/elevation
  language, radii, motion tone, explicit anti-patterns) **before** generating markup.
- R2. The committed artifact from R1 MUST be a concrete, DESIGN.md-compatible spec
  (palette with roles, type pairing, depth, radii, motion, anti-patterns). Whether
  that spec is *selected from a curated library* or *authored fresh* is a
  design/default choice (see OQ1), not a requirement.
- R3. Every produced design MUST be validated against a concrete **artifact
  contract** (a defined, checkable set of what a valid artifact must contain).
- R4. The agent MUST **render and visually inspect** its own output (screenshot)
  as part of the loop — not ship un-rendered markup.
- R5. A **separate critic pass** (independent of the generating step's self-judgment)
  MUST run and emit explicit, itemized must-fixes — including an anti-"branded-generic"
  check (do not reuse the same hero/cards/sidebar skeleton) and coverage of
  empty/error/loading states, accessibility, and responsive behavior.
- R6. At least **one revision pass** MUST run, carrying the must-fixes forward
  explicitly (each must-fix is tracked to resolution, not silently dropped).
- R7. The final deliverable MUST be **chat-ready**: the design HTML plus a rendered
  preview image, deliverable through the normal channel path (Slack/Discord/etc.).
- R8. The capability MUST work identically across Claude, Codex, and OpenCode
  agents (see C1).
- R9. **Cap semantics.** When the bounded loop hits its cap (C7) with unresolved
  must-fixes, the system MUST either (a) BLOCK chat-ready delivery if any unresolved
  finding is at or above a defined severity threshold, or (b) deliver while
  explicitly DISCLOSING the unresolved must-fixes in the artifact's evidence/trace.
  Silently shipping unresolved must-fixes as "done" is not allowed.

## Constraints

- [HARD] **C1 — Cross-provider parity.** The capability must be available and behave
  equivalently across claude/codex/opencode. Implementation must be provider-agnostic
  (mounted files + an instruction pattern), with no provider-specific generation code.
  (Project hard rule.)
- [HARD] **C2 — Render step must be at parity, fully defined.** Memory indicates
  Codex containers carry the `agent-browser` *skill file* but may NOT have the actual
  `agent-browser` *command*. Design MUST verify the live container image and guarantee
  an equivalent render capability across all provider containers (or a parity-clean
  fallback). "Parity" here means more than command availability — design MUST pin/define:
  (a) browser engine + version, or the accepted cross-provider variance; (b) the
  viewport set rendered; (c) asset/network behavior (offline/self-contained vs allowed
  fetches); (d) screenshot output format; (e) render-failure semantics; and (f) where
  render evidence/traces are stored. **Verified against the live image before design locks.**
- [HARD] **C3 — Credential model.** No raw API keys in containers; any external calls
  go through the OneCLI gateway. (No new secret surface introduced by this feature.)
- [HARD] **C4 — Context budget.** Design-system reference material must not be
  eager-loaded into every session (151 full systems would blow the context window).
  Reference data is read on demand.
- [HARD] **C5 — License.** Any assets vendored from Open Design (Apache-2.0) must
  carry attribution and the upstream license.
- [SOFT] **C6 — No new heavyweight runtime dependency.** Prefer reusing existing
  container capabilities (the skill mount, the existing render tool, `impeccable`)
  over adding new services or large packages.
- [HARD] **C7 — Bounded loop.** The revise loop MUST be bounded (an unbounded
  critic/revision loop is a cost + reliability failure). The *exact* cap is a default
  (≤3 rounds, see OQ5), but boundedness itself is non-negotiable. At the cap, R9 cap
  semantics apply.
- [HARD] **C8 — Artifact safety/packaging.** Because R7 delivers HTML through chat,
  generated artifacts MUST be self-contained or explicitly package their referenced
  assets, MUST NOT leak credentials or session/internal data, and MUST NOT include
  unsafe external scripts/network calls unless deliberately allowed and disclosed.

## Non-Goals (Explicitly Out of Scope)

- NG1. Integrating the Open Design daemon or its MCP server into nanoclaw. (Settled:
  redundant orchestrator-in-orchestrator; breaks parity; auth mismatch.)
- NG2. Document/media **exports** — PPTX, MP4, PDF. Reserved as a demand-gated
  "escape hatch" for a later phase; not part of v0.
- NG3. The Open Design Electron desktop app / canvas editing / in-place visual editing.
- NG4. A persistent design "memory" that accumulates the user's confirmed
  artifacts/palettes across sessions (a later enhancement).
- NG5. Non-UI design (brand strategy, copywriting as a standalone deliverable).

## Key Concepts

- **Design system (DESIGN.md):** A concrete, prescriptive spec — exact palette with
  semantic roles, type scale + pairing, depth/elevation philosophy, radii, motion,
  and explicit do/don'ts — used as a *generative target*, not abstract advice.
- **Author-then-conform:** Commit a full concrete design system first, then conform
  to it exactly; the opposite of generating from the model's default priors.
- **Render-grounded iteration:** Render the produced HTML, screenshot it, and judge
  the *rendered pixels* — not just the source — before revising/shipping.
- **Separate critic pass:** A judgment step independent of the generator's own
  self-scoring (e.g. `impeccable` + a distinct critic), since a model scoring its own
  output cannot reliably catch "it rated its own mediocre design highly."
- **Must-fix carry-forward:** Each itemized critic finding is tracked to explicit
  resolution across revision rounds, not silently dropped.
- **Artifact contract:** The defined, checkable set of requirements a produced design
  artifact must satisfy to be shippable.
- **Branded-generic:** The failure mode where a distinct palette/typography is wrapped
  around the same default layout skeleton — looks "branded" but is structurally generic.

## Open Questions (defaults chosen — flag if wrong)

- **OQ1 — How many design systems to vendor?** Defaulting to a **curated subset
  (~15–20)** of Open Design's 151 (app/product-oriented: linear, vercel, application,
  dashboard, clean, claude, etc.) plus an index, expandable later — rather than all 151.
  Rationale: C4 context budget; the rest are reference data that can be added on demand.
- **OQ2 — Critic composition for v0 (must be genuinely independent — R5).** Defaulting
  to **`impeccable` (deterministic tell-catcher) + a *fresh critic pass*** — a critic
  step that did NOT author the design, given only the rendered screenshot + DESIGN.md +
  the rubric and asked to find must-fixes. The agent's *own* self-review does NOT count
  as the independent critic (it would violate R5 and risks ritual-theater output). A
  *cross-model* critic (e.g. a different provider judging) is a later enhancement; the
  v0 independent critic is the fresh-pass + impeccable. Design must ensure the fresh
  pass is structurally separate from generation (e.g. a distinct sub-agent/turn).
- **OQ3 — Activation.** Defaulting to **explicit invocation plus design-intent
  detection** (the skill triggers when the agent is asked to design/build a UI).
  Exact trigger wording is a design detail.
- **OQ4 — Where it lives.** Defaulting to a **container skill mounted into every
  agent session** (parity-clean, all three providers consume mounted skills
  identically), rather than a per-group opt-in install. Design MUST verify actual
  provider consumption (Codex `$skill` / OpenCode surfacing) rather than assume it.
- **OQ5 — Loop cap value.** Defaulting to **≤3 revision rounds** (boundedness itself
  is HARD, C7). Alternative: a different fixed cap. Tunable later.

## Success Criteria

- SC1. Given a UI design request, an agent (on each of claude/codex/opencode) commits
  a concrete DESIGN.md, produces HTML conforming to it, renders+screenshots it, runs a
  separate critic that emits itemized must-fixes, completes ≥1 revision carrying those
  must-fixes forward, and delivers chat-ready HTML + a preview image.
- SC2. The same request on each provider exercises the same loop with no
  provider-specific code path (C1); the C2 render-parity question is resolved with a
  verified answer (works on all three, or a defined fallback).
- SC3. On a held-out design task, the output is demonstrably non-"branded-generic",
  measured against a **concrete rubric/fixture defined in design** (not just critic
  pass/fail): the rubric names a default layout skeleton and requires the output's
  structure to differ from it, and requires the anti-generic / empty-error-loading
  states / a11y / responsive checklist items to pass.
- SC4. The loop is bounded (C7) and its cap behavior is **observable**: at the cap,
  the final artifact carries a status (shipped / blocked), the list of any unresolved
  must-fixes with their severities, and which candidate was selected as "best" — per
  R9. "Graceful" = no unbounded looping and no silent shipping of unresolved must-fixes.
- SC5. No raw credentials enter containers (C3); no eager-loading of the full
  design-system corpus (C4); vendored assets are attributed (C5).
