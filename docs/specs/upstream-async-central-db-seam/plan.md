## 4. Design

### 4.1 Port verbatim, shim locally, ratchet the shim

Upstream's driver files land byte-identical and join the upstream manifest. The fork adds ONE local export in `src/db/connection.ts`:

```ts
export function getRawDb(): Database.Database { return sqliteRaw(getDb()); }
```

`sqliteRaw` is upstream's own escape hatch (used by its migration runner), so the shim is upstream-sanctioned. In PR 1 every `getDb()` call site is renamed to `getRawDb()` mechanically — zero semantic change, the tree builds, the driver exists with no callers. From PR 1 on, `src/db/raw-db-ratchet.test.ts` pins the set of `getRawDb` importers (file list, not a count, so a rename cannot hide growth): a PR may only remove entries; PR 6 pins the terminal allowlist (§4.5). Same mechanics as the seam-2 `computeOffenders` ratchet in `src/storage-manager.ts` and the upstream-ownership ratchet `update-nanoclaw-3` is building — reuse that helper if it has landed by PR 1; otherwise a 30-line local one.

**Raw and driver share one connection — the ordering rule that keeps that safe.** Upstream's `activeTransaction` gate serializes only driver `access()` calls; a raw statement bypasses it, and an async driver transaction yields at every `await`, so a raw statement running in an interleaved continuation would silently execute *inside* the open `BEGIN IMMEDIATE` (joining a transaction it knows nothing about, and rolling back with it) or throw `cannot start a transaction within a transaction`. Two consequences shape the whole series:

1. **Driver transactions are the last thing to land** (PR 6). Until then the fork has zero driver transactions: every converted site is a non-transactional `get/all/run`, which the driver executes synchronously on the same handle a raw call uses, and every fork transaction stays a raw *synchronous* `db.transaction(() => …)()` closure — which cannot be interleaved by anything, exactly as today. Raw and driver statements therefore coexist in PRs 1–5 with byte-identical semantics to the all-sync tree.
2. **In the terminal state, driver transactions and synchronous central blocks share one fork-level lease** (`src/db/central-lease.ts`, PR 6): `centralTransaction(fn)` = acquire the lease → `db.transaction(fn)` → release; `withCentralSync(fn)` = acquire the lease → run the synchronous block `fn` (guard evaluation + mailbox insert/spawn, or `withQuietInvalidationSync` + its write) → release. The lease is an `AsyncMutex` (the same shape as upstream's `drivers/shared.ts`, re-implemented in ~30 fork lines because upstream's instance is private to the driver). A sync block therefore never observes an open driver transaction and never has to refuse: it waits its turn (microseconds — closures are DB-only, §4.4) and then runs to completion with nothing interleaving. Non-transactional driver `get/all/run` do not take the lease; they never open a transaction, so a sync block cannot collide with them. The sync block's `withRawDb(fn)` additionally throws `RawAccessDuringTransactionError` if better-sqlite3 reports `db.inTransaction === true` — a belt that is unreachable by construction and counted in the gate (§6) as evidence. Deadlock analysis: a lease holder in a sync block cannot await; a lease holder in a transaction closure may await only driver calls (§4.4 AST test), never a mailbox, a container, or another lease — so no wait cycle exists. Sites that evaluate a guard inside a *synchronous* mailbox action (`container-runner.ts:744`, the memory-admission dequeue) take the lease **around** the mailbox action, not inside it.

### 4.2 Leaf + every importer in one PR; no transitional twins

A `*Sync` facade per leaf was considered and rejected in the plan review: a twin serving live traffic has no behavioral coverage while the leaf's tests are async, and (§4.1) a raw twin can interleave into a driver transaction. Instead each `src/db/*` leaf converts to async **together with every non-test importer**, so the type checker (no `.prepare` on `DbDriver`; `Promise<Row>` has no columns) forces every caller in the same commit and nothing transitional exists between PRs. Non-test importers per leaf on `origin/main`: `usage` 3, `provider-health` 4, `scheduled-tasks` 1, `dropped-messages` 2, `container-configs` 20, `agent-groups` 40, `messaging-groups` 35, `sessions` 47 — the last four overlap heavily, so they convert as one PR (PR 4, ~90 files) rather than four passes over the same importers. Inside an importer, only the statements that go through the converted leaf change; the importer's own direct SQL stays on `getRawDb()` until its owner's PR (PR 5), which §4.1 allows because no driver transaction exists yet.

**Leaf exports reachable from a raw transaction closure stay synchronous until PR 6.** A raw `db.transaction(() => …)()` closure is synchronous; an awaited call inside it commits before the continuation, and an un-awaited one lets the companion write and its rejection escape the transaction. Concretely `cli/resources/wirings.ts:333-339` calls `ensureAgentDestinationForWiring()` (messaging-groups leaf) inside an IMMEDIATE transaction with a parent-plus-companion rollback invariant. So PR 3/4 enumerate, per leaf, the exports invoked from any of the ten closures (the §4.4 AST test lists them) and leave those on the raw handle with **no async form** — they are not twins, they are simply not yet converted — and PR 6 converts each together with its closure. Their non-transactional callers keep calling the sync form until then.

### 4.4 Transactions (PR 6, all eleven at once)

All 11 central sync `.transaction(fn)` closures become `await db.transaction(async () => { … })` in ONE PR, with sequential awaits and **no non-DB statement inside**: mailbox writes, container ops, adapter calls, logging that awaits, all move after commit (upstream `driver.ts:41-46`). The 10 s watchdog is **detection, not prevention** — it is a `Promise.race` that rejects and rolls back the outer transaction while the closure body keeps running after its current await resolves, so an external effect inside a closure can still fire after rollback. The invariant is therefore enforced structurally: `src/db/transaction-closures.test.ts` uses the TypeScript checker (not text) to resolve the receiver of every `.transaction(` call in `src/`: before PR 6, a receiver typed `Database.Database` (raw) is allowed only in the eleven pinned central files (plus the sixteen non-central SQLite sites, listed separately) and a receiver typed `DbDriver` is forbidden everywhere (R4); from PR 6, the only allowed caller of `DbDriver.transaction` is `src/db/central-lease.ts`, every fork site goes through `centralTransaction`, and each closure may contain an `await` only on a driver call — any call into `session-manager`, `container-runner`, a channel adapter, `fetch`, or the lease itself fails the test. Positive fixtures for both receiver types are part of the test. Per-site tests assert the external effect happens only after commit and not at all on rollback (§8.6). `cli/crud.ts:268` `postCreate` flips to async here, not earlier, because it is the transaction contract that changes.

### 4.5 The two invariants that live in a primitive

**I-1 — guards and the quiet-invalidation write stay synchronous.** `WakeGuard`, `WriteGuard`, the agent-route guard (`targetWiredToMessagingGroup`) and `withQuietInvalidationSync` (`db/sessions.ts:276`, 12 callers — an "invalidate, then write, with nothing between" pair by the design of migration 068) read or write the central DB synchronously forever; they are never awaited. The primitive: `src/db/central-lease.ts` (new, PR 6) exports `centralTransaction(fn)`, `withCentralSync(fn)` (§4.1 — the lease that makes a sync block and a driver transaction mutually exclusive, so a legitimate write or wake is never refused by a timing coincidence), `withRawDb(fn)` (usable only inside `withCentralSync`; fail-closed on `inTransaction`) and `evaluateGuardSync(guard)`, which calls the guard and throws `GuardNotSynchronousError` if the result is thenable — a cast or accidentally-async guard is rejected at runtime at the evaluation site, not by convention. The plan-review finding stands corrected here: the write guard runs inside `withExistingMailboxSession`, whose action type admits promises (`session-manager.ts:522`), so the mailbox funnel is **not** the enforcing primitive; `evaluateGuardSync` is, and every evaluation site (`container-runner.ts:744,907,1309`, `session-manager.ts:1063,1132`, `sweep-container-health/index.ts:276`) goes through it. An AST test (`src/db/central-lease.test.ts`) asserts that in `writeSessionMessage` and the spawn path the `evaluateGuardSync(` call and the insert/spawn statement sit inside one `withCentralSync` block with no `await` between them, so the suspension window cannot be reintroduced by a later edit. `withQuietInvalidationSync` keeps its exact 068 contract ("in the same synchronous turn as that write") by running inside `withCentralSync` with its write. The terminal `withRawDb` allowlist (pinned by the ratchet in PR 6) is exactly: the three guard implementations, `withQuietInvalidationSync`, `modules/agent-to-agent/write-destinations.ts` (its `resolve()` — three central reads — runs inside the mailbox action immediately before a REPLACE-shaped `replaceDestinationRows`, so a yield between them could reinstate a destination an admin revoked; accepted 2026-09-04 at the seam-2 owner's request), `migrations/index.ts` (`sqliteOnly`), `storage-maintenance-worker-thread.ts`. Rule for every allowlisted sync block: it executes the leaf's exported SQL constants through `withRawDb` directly; it never calls an async leaf export and never gets a `*Sync` twin of one. Owner: runner-mailbox owner (this session).

**I-2 — a promise is never used as a boolean.** Where it lives: `@typescript-eslint/no-misused-promises` (`checksConditionals`), `no-floating-promises` and `await-thenable` under `projectService: true`, scoped to `src/**/*.ts` (`scripts/` keeps the non-type-aware config: `tsconfig.scripts.json` is not project-service-discoverable and upstream never lints `scripts/` at all). PR 0 found that **no hook or CI runs lint today and `pnpm run lint` is already red** (92 pre-existing errors, all under `src/`: no-unused-vars 38, no-require-imports 36, preserve-caught-error 7, others 11) — a rule nobody runs is prose, so PR 0b fixes those 92 at the root and adds `eslint src/ --quiet` (errors only; ~70 s type-aware, under `ionice -c3 nice -n 10`) to the husky `pre-push` hook and to the deployer's build guard. Changed-files-only linting was rejected: an async signature change in a leaf creates the `hasTable` inversion in an *untouched* importer, which only a full-tree type-aware pass sees. `hasTable` from `connection.ts` becomes async in PR 3 and its 9 truthiness sites convert in the same PR as their file (§7 table). Owner: deployer (PR 0/0b), then each PR owner.

## 9. Risks and unresolved decisions

- **R1 (highest):** a forgotten `await` on a `void`-returning write (e.g. `db.run` whose result is unused) is invisible to the type checker; only `no-floating-promises` catches it, and only a gate that runs makes it structural. PR 0 and PR 0b must be merged before PR 1's conversion commit.
- **R2:** the watchdog is detection only (§4.4); the structural closure test is the prevention. A site that legitimately needs >10 s of DB work is restructured, never exempted.
- **R3:** better-sqlite3 11 vs 13 API drift inside upstream's `sqlite.ts` — PR 1 runs upstream's conformance suite; a failure decides the bump question in run.md, not silently.
- **R4:** the raw/driver coexistence window (PRs 1–5) is safe only while zero driver transactions exist; `src/db/transaction-closures.test.ts` (PR 1) resolves every `.transaction(` receiver with the TypeScript checker and forbids a `DbDriver` receiver anywhere while pinning raw receivers to the ten files; PR 6 flips the assertion in the same commit that converts all ten sites.
- **R6:** the lease adds one async hop before every guarded write/wake and before every fork transaction. Cost is microseconds when uncontended; contention is bounded by DB-only closures; the >1 s WARN (§6) is the tripwire for a closure that got slow.
- **R5:** a second session editing the live checkout during a BUILD window (operator tools) — unchanged deploy protocol, detect via dirt + `/proc/*/cwd`.
- Unresolved (operator): none. Restart batching is the deployer's call within the protocol.
