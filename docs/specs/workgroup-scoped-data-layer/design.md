# Design: Workgroup-Scoped Data Layer for Sibling Agents

> Generated by `/team-design` — 2026-05-18
> Saved to: `docs/specs/workgroup-scoped-data-layer/design.md`

## Brief Reference

Formalize **workgroup** as a first-class layer above `agent_groups`. A workgroup pools chat archive, mnemon recall, and OneCLI secret declarations across member agent_groups (parent + codex twin and future siblings like `<x>-research`). Sibling agent_groups remain separate rows for routing/identity; workgroup is the layer above. See `brief.md` for full requirements and constraints.

## Options

### Option A: Workgroups table + workgroup_id column on agent_groups *(recommended)*

**Approach:** Add `workgroup_id TEXT` column to `agent_groups`. Add new `workgroups(id TEXT PRIMARY KEY, display_name TEXT, onecli_secrets TEXT JSON, created_at TEXT, updated_at TEXT)` table for canonical workgroup metadata. `container.json.workgroup_id` declares membership per group (operator-facing SoT). DB column carries the derived view used by projection queries.

**Pros:**
- Workgroup is a canonical DB entity — single query target for workgroup-level metadata
- OneCLI secret inheritance has a clean home (no scattered config across N member container.json files)
- Future workgroup-level fields (display_name, owner, archived_at, etc.) plug in via single ALTER TABLE
- Migration is one schema_version bump bundling schema + backfill (matches `031-inbox-board-foundations.ts` pattern)
- Projection query is a single subquery: `WHERE agent_group_id IN (SELECT id FROM agent_groups WHERE workgroup_id = ?)`

**Cons:**
- Two-table schema delta instead of one column
- container.json is the operator-facing SoT but the DB column is what projection queries hit — needs a reconciler when container.json changes (handled at create_agent and spawn paths; matches existing `agentGroupId` propagation pattern)

**Pattern alignment:** Matches CLAUDE.md § "Central DB" — shared metadata lives in `v2.db`, per-agent projection is the read interface. Mirrors how `messaging_groups` carries shared metadata that `messaging_group_agents` references via FK-like indirection.

**Confidence:** High — all components are already in the codebase, change is additive, no external dependencies.

**Assumptions:**
- `agent_groups.folder` (UNIQUE column) is sufficient to derive workgroup_id at migration time for current sibling pairs without operator action
- Operators are willing to declare `workgroup_id` in container.json for new groups going forward (matches the existing `agentGroupId` declaration pattern)

---

### Option B: Tag-only workgroup (no workgroups table)

**Approach:** Add `workgroup_id TEXT` column to `agent_groups` only. Workgroup-level OneCLI secrets live as a special key in EVERY member's container.json (e.g. `workgroupOnecliSecrets`). Workgroup is implicit — any distinct workgroup_id value defines one.

**Pros:**
- Schema is one new column; no new table
- No DB-to-FS reconciliation needed — container.json is sole SoT for both membership and secrets
- Smaller migration footprint

**Cons:**
- Workgroup-level secrets duplicated across N member container.json files; drift is operator's problem (the same kind of bug we just fixed with PR #105 for `MNEMON_STORE_<folder>` casing)
- No canonical "workgroup row" — can't enumerate workgroups except via `GROUP BY workgroup_id` on agent_groups; can't add workgroup-level metadata without rebuilding the pattern
- Future workgroup-level fields (display_name, owner, etc.) compound the duplication
- Doesn't match Central DB pattern for shared metadata

**Pattern alignment:** Partial — fits container.json-per-group convention but not Central DB shared-metadata convention. Pushes future complexity onto operators.

**Confidence:** Medium — works for the immediate need, accumulates cost as workgroup-level fields proliferate.

**Assumptions:**
- Workgroup-level metadata stays minimal forever (just OneCLI secrets)
- Operators tolerate manual cross-file sync

---

### Option C: Filesystem-driven workgroup config

**Approach:** New `groups/<workgroup>/workgroup.json` file declares workgroup metadata (display_name, onecli_secrets, members). Members' container.json declares `workgroup_id`. Optional DB column on agent_groups for fast lookup, populated by group-init / explicit sync step.

**Pros:**
- Workgroup config lives in its own file at a stable filesystem path
- Matches the existing `groups/<folder>/` convention for per-agent config
- No new DB table required if scope-resolver and projection both read filesystem

**Cons:**
- Where does `workgroup.json` live? At one designated member's folder (which?), or a new `workgroups/<id>/` top-level dir? Either way adds a new filesystem topology
- Two SoTs to keep in sync (workgroup.json + agent_groups DB column), unless we accept slower filesystem walks at spawn time
- Doesn't compose with the channel/provider skill installer pattern — those skills drop files into `groups/<folder>/`, not into a workgroup-level dir
- Filesystem walks at spawn time are slower than a JOIN; matters at high-frequency spawn paths

**Pattern alignment:** Partial — matches per-group filesystem pattern but creates a new layer not present elsewhere.

**Confidence:** Medium — workable but introduces a new abstraction layer; DB option is simpler and more consistent.

**Assumptions:**
- Operators are willing to maintain a workgroup-level filesystem topology
- Filesystem walks acceptable at spawn time (currently per-agent projections execute synchronously on every spawn)

## Recommendation

**Selected: Option A** — workgroups table + workgroup_id column on agent_groups.

**Justification:** Three observations make this dominant:

1. **Workgroup is shared metadata** — that's exactly what Central DB is for (CLAUDE.md § "Central DB"). Container.json is for per-group config; workgroup-level config belongs higher in the topology, in the DB.
2. **OneCLI secret inheritance needs a home.** Option B duplicates secrets across N container.json files — re-creating the exact class of bug we just fixed with PR #105 (drift between hand-edited config and runtime). Option C scatters secrets into filesystem with slower lookup. A `workgroups` table is the right shape.
3. **Future-proofing is cheap with Option A.** New workgroup-level fields are one ALTER TABLE. Options B and C compound their respective tax with each new field.

### Sub-decisions (folded into Option A)

- **Declaration model:** `container.json.workgroup_id` is operator-facing SoT. `agent_groups.workgroup_id` (DB column) is the derived/cached value used by hot-path queries. Reconciliation happens at create_agent path and on container spawn (host re-reads container.json and updates the DB row if workgroup_id changed).
- **Backfill heuristic:** suffix-strip `<x>-codex` → workgroup `<x>` IF a row in `agent_groups` exists with `folder = <x>`. Standalone (no match) → workgroup_id = own folder name (workgroup-of-1). Bidirectional check prevents accidental cross-tenant pairing.
- **Mnemon `'workgroup'` mode:** new 4th mode in `scope-resolver.ts`. Implementation walks container.json files (matches existing `getAllMemoryEnabledGroupIds` at `:40`), filters where `workgroup_id` equals the calling group's workgroup_id. Cached for 60s same as today.
- **Mnemon default scope flip:** change `getRecallScope` default from `'self'` to `'workgroup'` at `container-config.ts:74`. Safe because:
  - Standalone groups have workgroup_id = own id → workgroup-of-1 → same row set as `'self'`
  - Sibling pairs get pooled recall automatically (intended outcome)
  - Operators who want the old behavior set `recall_scope: 'self'` explicitly
- **OneCLI secret merge semantics:** workgroup baseline ∪ per-group additive. Computed in `container-runner.ts` (spawn path, around line 1787) before calling `applyOnecliSecrets`. Per-group cannot subtract — guards against a sibling silently weakening the shared baseline.
- **Drop in-container filters:** remove `WHERE agent_group_id = ?` from `resolve_thread_link` (`thread-search.ts:359-366`), `search_threads` (`:225`), and `read_thread` family. The projection now contains the entire workgroup; the in-tool filter would narrow back to self-only and defeat pooling.
- **Migration shape:** single migration `036-workgroup-id.ts` does schema (ADD COLUMN + CREATE TABLE) + backfill (suffix-strip + parent-existence) in one up() function. Matches `031-inbox-board-foundations.ts` bundling pattern.

**Confidence note:** High overall. Two areas of medium confidence:

1. **Suffix-strip heuristic** correctly handles all 10 of Dave's current pairs but is not future-proof for siblings like `<x>-research`. Acceptable trade-off — brief says explicit `workgroup_id` declaration is the long-term path; the heuristic is a one-time migration convenience.
2. **Default scope flip from `'self'` to `'workgroup'`** is behavior-changing for any installation that had implicit `'self'` reliance. Mitigated because (a) standalone groups behave identically, (b) sibling pooling is the intended outcome documented in the brief, (c) operators can set `recall_scope: 'self'` to restore prior behavior. Worth calling out in QA so we explicitly verify a known thread post-migration.

## MVP Scope Boundary

### IN scope (first ship)

- **Migration 036:** `ADD COLUMN agent_groups.workgroup_id`; `CREATE TABLE workgroups`; backfill via suffix-strip + parent-existence heuristic
- **`src/db/per-agent-projections.ts`:** workgroup-scoped projection in `buildArchiveProjection` and `buildCentralProjection` — `WHERE <filter_col> IN (SELECT id FROM agent_groups WHERE workgroup_id = ?)`
- **`src/modules/memory/scope-resolver.ts`:** `'workgroup'` mode
- **`src/container-config.ts`:** `workgroup_id?: string` on `ContainerConfig`; default flip in `getRecallScope` to `'workgroup'`
- **`src/onecli-secrets.ts` + spawn path in `src/container-runner.ts`:** workgroup baseline ∪ per-group additive UNION before `applyOnecliSecrets`
- **`container/agent-runner/src/mcp-tools/thread-search.ts`:** drop `agent_group_id = ?` from `resolve_thread_link` / `search_threads` / `read_thread`
- **Tests:** unit coverage for projection workgroup-scoping, `'workgroup'` scope mode, OneCLI secret merge, backfill heuristic, mnemon default flip
- **Docs:** new `docs/workgroups.md`; update `CLAUDE.md` § "Entity Model" and § "Secrets / Credentials / OneCLI" to reference workgroups

### OUT of scope (deferred)

- **Conversations folder cross-access** — brief non-goal; future `read_peer_conversations` tool
- **`MNEMON_STORE_<folder>` env override deprecation** — brief non-goal; later cleanup PR
- **Admin UI for workgroups** — brief non-goal; declarative config only
- **Cross-workgroup data sharing** — brief non-goal (boundary stays at workgroup)
- **Slack user-token via OneCLI (Q1)** — separate follow-on; consumes workgroup secret inheritance but ships independently
- **Workgroup-level display name beyond seeded value** — column exists for future UI but no consumer in MVP
- **Migration of existing duplicate per-group `onecliSecrets` to workgroup level** — operator action post-migration; tooling not required
- **Workgroup reconciler daemon** — minimal reconciliation happens on spawn (host re-reads container.json on every container start); a separate periodic reconciler isn't required for MVP

## Decision Record Updates

**Decisions:**

- **D5:** Chose Option A (workgroups table + workgroup_id column on agent_groups). Rejected: Option B (tag-only — duplicates workgroup-level config across N container.json files, drift trap) and Option C (filesystem-driven workgroup.json — new topology layer not present elsewhere, slower lookup). Constraint refs: [C1, C2, C3]. Affects groups: [TBD — populated by /team-plan].
- **D6:** Backfill heuristic = suffix-strip `<x>-codex` + bidirectional parent-existence check. Rejected: prefix-match (ambiguous on `<x>-bot-codex` style names); explicit-only (violates R6's "auto-pair without operator action"). Constraint refs: [C7].
- **D7:** Mnemon default scope flips from `'self'` to `'workgroup'` at `getRecallScope` default in `container-config.ts:74`. Rejected: keep `'self'` default and require explicit `recall_scope: 'workgroup'` per group (more conservative but requires 10+ container.json edits on Dave's install and defeats the auto-pairing benefit of R6). Constraint refs: [C4].
- **D8:** OneCLI secret merge semantics = workgroup baseline ∪ per-group additive (UNION, additive-only). Rejected: per-group replaces workgroup (a sibling could silently weaken the shared baseline); strict workgroup-only (defeats per-group tool-specific secrets like a single group needing Datafold). Constraint refs: [].
- **D9:** Drop in-container `WHERE agent_group_id = ?` from thread tools. Rejected: keep filter but add workgroup-aware variant (defeats pooling intent — projection already bounds visibility, in-tool filter would only narrow). Constraint refs: [C1].

**Constraints added:** none beyond brief — all C1–C8 carry forward.

**Assumptions added:** A1–A7 above.
