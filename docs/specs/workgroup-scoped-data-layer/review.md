## MUST-FIX Findings (cycle 2)

### [M1] Mnemon store routing silently disconnects existing stores (DATA LOSS RISK)

- **Raised by:** Reviewer A (#2 HIGH), Reviewer C (#2)
- **Finding:** Existing mnemon stores are keyed on `agent_groups.id` (verified empirically): illie's store is at `~/.mnemon/data/ag-1776377699463-2axxhg/mnemon.db` with **43MB of accumulated facts**. The design sets `workgroups.mnemon_store_id` default = `workgroups.id` = folder slug (e.g., `"illysium"`). Post-migration, `container-runner.ts:1775` would compute `MNEMON_STORE=illysium`, mnemon recall lands in a non-existent store, and all 43MB of recall history becomes unreachable to the agent.
- **Effort to Fix:** Low — one backfill statement in migration 036.
- **Impact if Ignored:** Critical — silent user-visible data loss for every workgroup-paired group on Dave's install. Violates C3 (no data loss).
- **Suggested resolution:** Migration 036 must backfill `workgroups.mnemon_store_id` to the **parent member's existing `agent_groups.id`** for paired workgroups (e.g., workgroup `illysium` → `mnemon_store_id = 'ag-1776377699463-2axxhg'`). Standalone workgroups get `mnemon_store_id = own agent_groups.id`. Verified: Reviewer A confirmed empirical store locations via `mnemon store list` and `du`.
- **Fact-check:** Verified — `mnemon store list` shows stores keyed by `agent_groups.id` (e.g., `ag-1776377699463-2axxhg`).
- **Status:** Open

### [M2] W1 NOT NULL constraint cannot be installed via `ALTER TABLE ADD COLUMN`

- **Raised by:** Reviewer A (#1 HIGH), Reviewer B (NOT-NULL contract phase, LOW), Reviewer C (#4)
- **Finding:** Design schema declares `ALTER TABLE agent_groups ADD COLUMN workgroup_id TEXT REFERENCES workgroups(id)` and claims W1 (NOT NULL) "via table rebuild OR a separate ALTER (SQLite limitations apply)" — but the migration shape pseudocode at lines 286-319 does neither. SQLite documentation: cannot `ADD COLUMN NOT NULL` on a populated table with `DEFAULT NULL`; cannot `ADD CONSTRAINT` after the fact; the textbook expand-contract path requires a table rebuild (`CREATE TABLE new → INSERT SELECT → DROP → RENAME`).
- **Effort to Fix:** Medium — commit to table-rebuild in migration 036 (single transaction-wrapped).
- **Impact if Ignored:** High — W1 is application-level only; future call sites inserting `agent_groups` rows without `workgroup_id` produce silent NULLs that trip W3 only at next spawn, not at insertion site. Schema constraint is the right floor.
- **Suggested resolution:** Migration 036 rewrites `agent_groups` via the SQLite standard table-rebuild dance:
  ```sql
  CREATE TABLE agent_groups_new (... workgroup_id TEXT NOT NULL REFERENCES workgroups(id), ...);
  INSERT INTO agent_groups_new SELECT ... FROM agent_groups; -- post-backfill data has workgroup_id populated
  DROP TABLE agent_groups;
  ALTER TABLE agent_groups_new RENAME TO agent_groups;
  ```
  All inside the single transaction. Order: CREATE workgroups → backfill workgroups rows → rebuild agent_groups → verify W1/W2 → bump schema_version.
- **Fact-check:** Verified — SQLite.org ALTER TABLE docs (T1) and Reviewer A's empirical test against better-sqlite3.
- **Status:** Open

### [M3] Dedup query missing required `id` column and other non-aggregated columns

- **Raised by:** Reviewer A (#5 HIGH)
- **Finding:** Design § "Pooled archive dedup (M4)" shows pseudocode with `<other_cols_via_aggregation>` placeholder. `messages_archive.id` is PRIMARY KEY (per `message-archive.ts:68`); the projection INSERT requires `id`. Missing columns: `channel_type` (NOT NULL), `channel_name`, `platform_id`, `sender_id`, `sender_name`, `created_at`. Without explicit aggregators, SQLite picks arbitrary values — non-deterministic across spawns.
- **Effort to Fix:** Low — write the full column list with MIN/MAX explicitly.
- **Impact if Ignored:** High — pseudocode is unimplementable as written; first implementation attempt either fails NOT NULL constraint or produces inconsistent rows.
- **Suggested resolution:** Replace the pseudocode with the full column list (per Reviewer A's resolution):
  ```sql
  SELECT MIN(id) AS id,
         MIN(agent_group_id) AS agent_group_id,
         messaging_group_id,
         MAX(channel_type) AS channel_type,
         MAX(channel_name) AS channel_name,
         MAX(platform_id) AS platform_id,
         thread_id, role,
         MAX(sender_id) AS sender_id,
         MAX(sender_name) AS sender_name,
         text, sent_at,
         MIN(created_at) AS created_at
    FROM messages_archive
   WHERE agent_group_id IN (SELECT id FROM agent_groups WHERE workgroup_id = ?)
   GROUP BY messaging_group_id, thread_id, role, sender_id, sent_at, text
  ```
- **Fact-check:** Verified — `message-archive.ts:67-81` schema; `per-agent-projections.ts:73-87` ARCHIVE_COLS array.
- **Status:** Open

### [M4] Dedup GROUP BY narrative is incorrect; assistant rows survive by accident not by design

- **Raised by:** Reviewer A (#7 HIGH), Reviewer C (#5)
- **Finding:** Design § "Pooled archive dedup (M4)" claims "Assistant messages are unique per agent (each sibling writes its own response); they survive GROUP BY because their text differs." Reviewer A traced `delivery.ts:688-701`: assistant rows survive because `sent_at` differs (sequential delivery) OR text differs. If two siblings ever produced identical text + identical sent_at (templated greeting at session-start race), dedup would silently delete data. The correct invariant: `sender_id` is unique-per-agent for assistant rows.
- **Effort to Fix:** Low — add `sender_id` to GROUP BY.
- **Impact if Ignored:** High — design correctness depends on an accidental invariant that future changes could break silently.
- **Suggested resolution:** GROUP BY includes `sender_id`: `GROUP BY messaging_group_id, thread_id, role, sender_id, sent_at, text`. For user rows: `sender_id` is the same originating user across both sibling archive copies → dedup still works. For assistant rows: `sender_id = agent_group_id` (per `delivery.ts:697`) differs per sibling → guaranteed distinct. Update the narrative.
- **Fact-check:** Verified — `delivery.ts:697` `senderId: session.agent_group_id` for assistant writes; `router.ts:793,916,932` for inbound user writes.
- **Status:** Open

### [M5] Backfill loop silently mis-classifies orphan `-codex` rows as standalone

- **Raised by:** Reviewer A (#9 HIGH)
- **Finding:** Migration pseudocode at lines 297-308 initializes `suffix_strip_unmatched: []` (line 318) but the loop never appends to it. The condition `if (wg === row.folder) standalone.push(row.folder)` traps `-codex` rows whose parent doesn't exist (e.g., `lone-codex` with no `lone` parent) → categorized as `standalone`. The S7 backfill report claims to flag these via `suffix_strip_unmatched`, but the pseudocode renders that array empty.
- **Effort to Fix:** Low — restructure the loop.
- **Impact if Ignored:** Medium — orphaned twins silently treated as standalone; operator can't audit. Violates the explicit "report-and-confirm" intent of S7.
- **Suggested resolution:** Per Reviewer A:
  ```typescript
  for (const row of rows) {
    let wg: string;
    if (row.folder.endsWith('-codex')) {
      const parent = row.folder.slice(0, -'-codex'.length);
      if (folderSet.has(parent)) {
        wg = parent;
        pairings.push({child: row.folder, parent});
      } else {
        wg = row.folder;
        suffix_strip_unmatched.push(row.folder);
      }
    } else {
      wg = row.folder;
      standalone.push(row.folder);
    }
    insertWg.run(wg, wg);
    updateAg.run(wg, row.id);
  }
  ```
- **Fact-check:** Verified — pseudocode trace.
- **Status:** Open

### [M7] Scope-resolver `'workgroup'` mode has two incompatible return contracts (member ids vs store id)

- **Raised by:** Reviewer C (#1)
- **Finding:** Design § M6 mnemon store routing says `'workgroup'` returns SINGLE `workgroups.mnemon_store_id`. Design § S4 calling-group-first invariant says `'workgroup'` returns `[callingGroupId, ...otherMembers]`. These are different APIs. The first is for `MNEMON_STORE` env injection at spawn; the second is for `mnemon recall --store` fan-out per member.
- **Effort to Fix:** Low — split the contract.
- **Impact if Ignored:** High — implementer satisfies one and breaks the other; mnemon recall may pass group_ids where store_ids are expected (recall comes back empty).
- **Suggested resolution:** Two distinct functions:
  - `resolveWorkgroupMembers(callingGroupId): string[]` — returns `[callingGroupId, ...otherMembers]` (used by scope-resolver for any future fan-out, and by tests asserting calling-group-first invariant)
  - `resolveWorkgroupStoreId(callingGroupId): string` — returns the single canonical store id (used by `container-runner.ts:1775` for `MNEMON_STORE` env)

  Document both. The existing `resolveRecallScope` signature returns `string[]` — for `'workgroup'` mode it returns `[resolveWorkgroupStoreId(callingGroupId)]` (a single-element array, engaging the `groupIds.length <= 1` fast path at `mnemon-impl.ts:228`).
- **Fact-check:** Verified — `mnemon-impl.ts:225-279` fan-out path; `mnemon-impl.ts:228` single-store fast path.
- **Status:** Open

## SHOULD-FIX Findings (cycle 2)

### [S1] M2 identifier semantics asymmetry (codex twin ids ARE folder slugs)

- **Raised by:** Reviewer A (#3 MEDIUM)
- **Finding:** Codex twins' `agent_groups.id` equals their folder slug (e.g., `illysium-codex`). Design's "opaque vs slug" contrast holds only for parent groups.
- **Suggested resolution:** Reword M2 to acknowledge asymmetry: "For parents, `workgroup_id = agent_groups.folder ≠ agent_groups.id`. For codex twins, `agent_groups.id = agent_groups.folder = workgroup_id`." Add a CHECK constraint on `workgroups.id` to forbid opaque-id contamination: `CHECK (id GLOB '[a-z0-9-]*' AND id NOT LIKE 'ag-%')`.
- **Status:** Open

### [S2] S3 reconciliation TOCTOU window

- **Raised by:** Reviewer A (#4 MEDIUM), Reviewer C (#3)
- **Finding:** Pseudocode reads `dbCurrent` BEFORE entering the transaction.
- **Suggested resolution:** Compress to single conditional UPDATE: `UPDATE agent_groups SET workgroup_id = ? WHERE id = ? AND (workgroup_id IS NULL OR workgroup_id != ?)`. Atomic check-and-set. Use `INSERT INTO workgroups ... ON CONFLICT(id) DO NOTHING` instead of `INSERT OR IGNORE`.
- **Status:** Open

### [S3] FTS rowid non-determinism after dedup

- **Raised by:** Reviewer A (#8 MEDIUM)
- **Finding:** Without `ORDER BY` in dedup SELECT, surviving rows pick non-deterministic rowids → snippet preview text can flip between spawns.
- **Suggested resolution:** Use `MIN(id)` for the surviving row's id (deterministic). Already covered by M3 resolution.
- **Status:** Open (resolved transitively by M3 fix)

### [S4] S8 structural test bidirectional

- **Raised by:** Reviewer A (#10 MEDIUM)
- **Finding:** S8 only enforces no orphan `messages_archive` queries outside the chokepoint; doesn't assert that `backlog.ts` / `server.ts` retain their `WHERE agent_group_id = ?` filters as defense-in-depth.
- **Suggested resolution:** Strengthen S8: (a) no orphan archive queries; (b) backlog_items/ship_log/tasks queries MUST contain `WHERE ... agent_group_id = ?`; (c) server.ts orchestrator query MUST contain `WHERE agent_group_id = ?`.
- **Status:** Open

### [S5] No operator write-path for `workgroups.onecli_secrets` (feature ships dormant)

- **Raised by:** Reviewer A (#11 MEDIUM), Reviewer C (#6)
- **Finding:** D8 writes `'[]'` to `workgroups.onecli_secrets` at backfill. No CLI/tool to populate it post-migration. Feature ships dormant.
- **Suggested resolution:** Add `scripts/set-workgroup-secrets.ts` to MVP IN-scope — small CLI that calls `resolveSecretUuids`, validates names, writes JSON to the workgroups row. Operator-facing.
- **Status:** Open

### [S6] Backfill report log files (`logs/migration-036.log`) never created in pseudocode

- **Raised by:** Reviewer A (#12 MEDIUM)
- **Finding:** Pseudocode line 318 uses `log.info(...)` which routes to `logs/nanoclaw.log`, not the dedicated file the design implies.
- **Suggested resolution:** Migration up() does `fs.writeFileSync(path.join('logs', 'migration-036.log'), JSON.stringify({pairings, standalone, suffix_strip_unmatched}, null, 2) + '\n')` after the SQL transaction commits. Same for `logs/migration-036-secrets.log`.
- **Status:** Open

### [S7] Container.json writes have no rollback path

- **Raised by:** Reviewer A (#13 MEDIUM)
- **Finding:** SQL transaction commits, then container.json filesystem writes happen — if writes fail (permission, disk full), DB says workgroup-paired but container.json still says `recall_scope: 'self'`. Spawn-time reconciler only fixes `workgroup_id`, not `recall_scope`.
- **Suggested resolution:** Migration runs FS writes after SQL transaction commits, with explicit try/catch and a failure path that logs prominently: "SQL portion succeeded; FS writes failed — run `scripts/migration-036-fs-writes.ts` to retry." The retry script reads `agent_groups.workgroup_id`, computes which groups should have `recall_scope: 'workgroup'`, and updates container.json idempotently.
- **Status:** Open

### [S8] Slug-as-PK is mainstream drift away from (GitHub 2024 client_id evidence)

- **Raised by:** Reviewer B (MEDIUM)
- **Finding:** GitHub's 2024 changelog explicitly moved away from slug-as-identifier toward opaque client_id, citing immutability and global-uniqueness. Design's `workgroups.id = folder slug` invites rename cascade issues.
- **Suggested resolution:** Document the trade-off in design. For MVP (10 sibling pairs, no rename activity), slug-as-PK is acceptable. Add CHECK constraint (covered by S1) to prevent opaque-id contamination. If renames become a thing, future migration adds an opaque PK with slug as UNIQUE column.
- **Status:** Open

### [S9] Spawn-only reconciliation has staleness window

- **Raised by:** Reviewer B (MEDIUM)
- **Finding:** Long-running containers hold stale `workgroup_id` between container.json edits and next restart.
- **Suggested resolution:** Document the staleness window in `docs/workgroups.md`. Optional: add a `/reconcile-workgroups` admin command for operator-triggered re-read without spawn. Out of scope for MVP per design's "Workgroup reconciler daemon — out of scope".
- **Status:** Open
