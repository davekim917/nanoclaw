## 2. Research Notes (grounding)

- **All five mutation primitives exist** host-side in `src/modules/scheduling/db.ts`: `cancelTask` (:43), `pauseTask` (:51), `resumeTask` (:59), `updateTask` (:78 — merges ONLY `prompt`/`script` into content plus `recurrence`/`process_after` columns; it cannot write arbitrary content keys), `insertTask` (:17).
- **`scheduleTask`'s `TaskDef` has NO `script` field** (`src/db/scheduled-tasks.ts:32-80`; content assembly at :179-183 builds `{prompt, quietStatus?, flagIntent?}`) — a naive move would silently drop the pre-task script. §4.2 addresses this.
- **`wakeContainer(session)`** importable host-side (`actions.ts:47`) — run-now wakes immediately.
- **Read-path cost (measured, honestly):** the CLI inventory completes in ~1.5s wall *including tsx process startup*; the in-process assembly itself is a few hundred ms of synchronous better-sqlite3 work across ~36 inbound + ~36 outbound read-only opens. Synchronous = event-loop-blocking (§4.9).
- **Frontend stack:** React + SWR + SSE `subscribe('session_event', …)` with 300ms trailing debounce (`dashboard/src/views/InboxBoard.tsx:69-104`). `BoardRoute` union (`BoardShell.tsx:19`) extends to `'scheduled'` (union type + `RouteNav` + any exhaustive switch).
- **SSE scope safety:** every frame is filtered per-connection by `_scopeAllows(conn.scopes, groupId)` (`src/dashboard/api/events.ts:92,117-120`) keyed on the frame's `agent_group_id` — safe to reuse `session_event`, provided board-relevant emits always carry the owning group id (never null).
- **Secret scope sources:** per-group `onecliSecrets` (`container_configs`, central DB) ∪ workgroup baseline (`workgroups.onecli_secrets`).
- **Sibling channel mapping (A1, resolved):** same `platform_id`, sibling-variant `channel_type` (`discord` ↔ `discord-codex` ↔ `discord-opencode`), each its own `messaging_groups` row.
- **Recurrence advance ordering:** `handleRecurrence` inserts the successor THEN clears recurrence on the completed row (`recurrence.ts:36-37`); a cron-parse error is caught and logged but NOT rethrown (`recurrence.ts:46-52`) — the row stays terminal-with-recurrence forever and the series silently strands. This is the residual silent-strand signature (§4.1).

## 3. Options

### 3a. Read-side architecture

**Option A — On-demand sweep, chunked async, short TTL cache (recommended).**
GET handlers assemble the fleet snapshot by opening each authorized group's session DBs read-only — **one session per event-loop tick via `setImmediate` chunking** — compute latest-row-per-series + capped history, join central DB, memoize in-process for 5s. All board DB opens use `{readonly: true}` + `busy_timeout = 1000` (the `hasPendingRecurrence` precedent, `sessions.ts:123`) — never the write path's 5000ms. Cold-cache requests await the in-flight assembly promise (single-flight); SWR's loading state covers the sub-second wait. **Read-your-own-write via generation counter:** a mutation bumps a generation integer and invalidates the cache; an assembly stamps the generation it started under and refuses to populate the cache if stale (an in-flight assembly that pre-read the mutated DB can otherwise repopulate a pre-mutation snapshot). **Degraded contract:** assembly is instrumented; warm assembly >1s logs a warning, >3s serves the last cache with `degraded: true`, which the health strip renders visibly.
- Pros: zero new state (nothing can drift from truth — the class of failure that bit scheduling twice); chunking keeps delivery polls and SSE writes responsive during assembly; TTL absorbs SSE-burst refetches (worst case one cold assembly per 5s window).
- Cons: snapshot ≤5s stale after external changes; a burst straddling TTL expiry pays one assembly.
- Pattern alignment: `api/tasks.ts` merge-on-read of session DBs.
- Confidence: **High**.
- Assumptions: fleet stays O(10²) series / O(10²) DBs; at 10× scale the chunked assembly grows linearly but stays non-blocking.

**Option B — Materialized index table refreshed by host-sweep.** Rejected: a second copy of scheduling state that can silently drift (both prior incidents were derived-state-diverged-from-truth failures); write load for an occasionally-open view; more code + migration + invalidation contract.

### 3b. Mutation API shape

**Option A — Resource + verb endpoints under `/dashboard/api/scheduled` (recommended).**
```
GET    /dashboard/api/scheduled                      → list (scope-filtered, health-derived)
GET    /dashboard/api/scheduled/:key                 → detail (full prompt/script, history, audit tail) — scope-filtered, 404 out-of-scope
PUT    /dashboard/api/scheduled/:key                 → edit {prompt?, script?, cron?}
POST   /dashboard/api/scheduled/:key/pause           → pause
POST   /dashboard/api/scheduled/:key/resume          → resume (recomputes next slot)
POST   /dashboard/api/scheduled/:key/run-now         → early-fire
POST   /dashboard/api/scheduled/:key/cancel          → end series
POST   /dashboard/api/scheduled/:key/move/preview    → dry-run: wiring check + secret delta (no write) — gated at MUTATION tier (§4.5)
POST   /dashboard/api/scheduled/:key/move            → execute move {targetAgentGroupId, targetMessagingGroupId, confirmedDelta}
```
`:key` = base64url of `agentGroupId / sessionId / seriesId` — a **locator, never an authz input** (§4.5). Stale keys (series moved/ended since list): every mutation helper returns touched-count; `touched === 0` maps to HTTP 409 `{reason:'stale_key'}`, forcing a client refetch — never a silent no-op. Route named `scheduled` per the brief's naming note (the `tasks` namespace belongs to the spawn board).
- Confidence: High. (Option B — single RPC endpoint — rejected: per-verb gates degenerate into a switch; foreign to the route table.)

### 3c. Board layout (two structural alternatives)

**Layout 1 — Health-lane kanban** (Stalled / Paused / Healthy / One-offs lanes, mirroring InboxBoard). Rejected: degenerate column shapes (healthy ≈ 90% of rows → one giant column), and lanes hide the group-by-agent-group axis the operator scans by.

**Layout 2 — Health strip + grouped list + detail drawer (recommended).**
Top: health summary strip (stalled / paused / healthy / one-off counts; stalled items enumerated inline, always first). Body: collapsible agent-group sections; each row = series (name, channel, cron + next fire UTC/local, ownership badge, health pill, last-fired). Row click opens a right-side drawer: full prompt + script, per-fire overrides (`quietStatus`, `flagIntent` model/effort — brief-required metadata), edit form, fire history (last 5), audit tail, verb buttons. Toolbar: group filter (existing `useGroupFilter`), ownership filter, health filter, free-text search. Drawer renders read-only on mobile (v1).
- Pros: density fits 30–60 rows; matches the scanning axis; unhealthy-first via strip + sort; reuses `BoardFrame`/`BoardBrand`/`RouteNav`/`GroupTitle` unchanged. Cons: new drawer primitive (~150 lines).
- **[RENDER-CHECK NEEDED]**: health-pill palette (stalled = attention-red on dark card background) introduces token combinations absent from existing views — validate contrast by rendering before finalizing.

## 4. Key Mechanism Designs

### 4.1 Health derivation (the load-bearing requirement)

For each series' live row (`status IN ('pending','paused')`):
```
interval  = next two cron-parser occurrences diff (parse identical to firing path:
            CronExpressionParser.parse(cron, { tz: TIMEZONE }) — recurrence.ts:31, TIMEZONE from src/config.ts)
overdueBy = now − process_after
state     = paused      if status='paused'
          = processing  if a processing_ack row exists for the live row id
                        (outbound.db opened read-only; stale claims self-heal via ack-clear
                         on container start)
          = unknown     if outbound.db is absent/unreadable AND the row is overdue —
                        observability failure is NOT collapsed into "not claimed"; the pill
                        renders grey and verb confirms display the substate
          = stalled     if overdueBy > max(interval × 0.5, 2 × SWEEP_INTERVAL)   // grace: late ≠ dead
          = healthy     otherwise
```
**Residual-strand detection (no live row):** a series whose newest row is terminal (`completed`/`failed`/`expired`) with `recurrence` still set is flagged **stalled** once `now − max(row.timestamp, process_after) > 2 × SWEEP_INTERVAL` — a stateless persistence clock (`messages_in.status_changed` exists in live DBs but is legacy/unwritten; the design stays zero-state). The grace window excludes the legitimate transient between completion-sync and successor-insert. This is the swallowed-cron-parse-error signature (`recurrence.ts:46-52` catches and logs without rethrow — `handleRecurrence` retries and fails every sweep, never inserting a successor). Note the insert-then-clear ordering (`recurrence.ts:36-37`) means a crash between the two steps yields a *duplicate successor* on the next sweep, not a strand — duplicates surface on the board as two live rows in one series, also flagged.
**Duplicate-successor detection:** the latest-row-per-series read shape (MAX(seq)) shows ONE row — a duplicate live successor would hide behind it while still able to fire. A separate cheap detector runs in the same assembly: `SELECT series_id, COUNT(*) FROM messages_in WHERE status IN ('pending','paused') AND kind='task' GROUP BY series_id HAVING COUNT(*) > 1` — duplicate series are flagged unhealthy and list/detail return ALL live rows for them.
Status alone is never the signal (brief D6). One-offs: same overdue check with interval = 2 sweeps.
Fire history (drawer): last 5 rows per series — `completed` + `messages_out` reply (`in_reply_to` = row id, ts ≥ due) → *ran*; `completed` + no reply → *completed (no chat output)*; `failed` → *failed*; `expired` → *missed*; board-cancelled (audit join, §4.3) → *cancelled*.
⚠️ **Brief amendment #2 (flagged for gate approval):** the brief's history states include "skipped/gated by pre-task script" as distinct, but the firing path records script-gated rows as plain `completed` (`container/agent-runner/src/poll-loop.ts:222-227`) with no persisted outcome marker — distinguishing them would require the container to write a new outcome signal, touching firing-path semantics (C1). v1 merges the two under *completed (no chat output)*; a persisted fire-outcome record is the v2 path.

### 4.2 Move sequencing (cancel-first with compensation)

```
preview: 0. authz: canManageScheduled(actor) — same tier as execute (§4.5); 404 otherwise
         1. resolve target MG (translate channel_type to target group's variant, same platform_id)
         2. run scheduleTask's wiring validation logic WITHOUT writing
         3. compute secret delta: effective(target) − effective(source),
            effective = group onecliSecrets ∪ workgroup baseline
            (NAMES/UUIDs only — values never leave the OneCLI gateway, never resolved host-side;
             enumeration bounded to source∪target effective sets, never a vault listing)
         4. return {wiringOk, gains[], losses[], crossWorkgroup, scriptPresent, deltaHash,
                    environmentDeltaChecked: false}
            — the secrets delta is checked; the target container's wider environment
            (packages, MCP servers, mounts, provider) is NOT — the confirm UI carries a
            static caveat; config-delta preview is a v2 item (§5 OUT)

execute: 0. authz + scope re-check from the decoded :key and body, independent of any prior
            preview call (preview is not a capability grant; :key is a locator, not authz)
         1. re-compute secret delta; if hash ≠ client-echoed confirmedDelta → 409 delta_changed
            (forces re-confirm; closes the preview→execute TOCTOU)
         2. snapshot source live row (content incl. script, recurrence, process_after, overrides)
        2a. in-flight guard: 409 `source_busy` if the source row is claimed (processing_ack,
            best-effort read) OR `process_after ≤ now` — moving a due/running fire would let
            the container complete the source turn while the target row fires too (double-fire).
            Residual ms-window between guard-check and cancel is documented and accepted.
        2b. durable intent: write a `move_intent` row to scheduled_audit BEFORE cancelling —
            a crash between steps 3 and 4 otherwise loses the series invisibly (recurrence
            cleared ⇒ the strand detector is blind). An unresolved intent (no live row
            fleet-wide for the series) surfaces as stalled on the board; it auto-resolves
            the moment a live row exists. (Compensating-transaction durable-record practice.)
         3. cancelTask(source)                      // live row → completed, recurrence cleared
         4. scheduleTask(target, snapshot)          // fail-closed insert; processAfter = snapshot.process_after
                                                    // (schedule PRESERVED — see note below)
         5. on step-4 failure: restore source via `restoreTaskRow` — an `insertRecurrence`-shape
            raw insert (db.ts:149-170) that preserves series_id, recurrence, content, and
            destination columns. NOT `insertTask` (sets series_id = new id, severing identity)
            and NOT `scheduleTask` (requires cron, re-runs destination validation mid-failure)
            — if the target insert SUCCEEDED, never delete it during any compensation path:
              target-live is the fail-closed partial-move state (a live series in the wrong
              place beats an invisible dead one)
            — if BOTH target insert and source restore fail, the series has zero live rows and
              recurrence cleared everywhere → invisible to the recurrence-filtered read shape
              AND to getCompletedRecurring. Write a durable `move_restore_failed` repair record
              to scheduled_audit BEFORE returning the error; the board's health strip surfaces
              audit-only repair rows as stalled entries until resolved
         6. verify invariant: exactly one live row fleet-wide for series_id; log + alert on violation
         7. audit row (§4.4)
```
- **Recurring-series only:** move is disabled for one-off tasks in v1 (UI-disabled, like thread loops). `TaskDef.cron` is a required string written unconditionally into `recurrence` (`scheduled-tasks.ts:32-37, 196-212`) — a one-off move would fail the type or manufacture the swallowed-parse strand signature in the target. One-offs keep visibility + cancel (consistent with D4's scope).
- **Script preservation:** `TaskDef` gains an optional `script?: string` field and the content assembly includes it (`scheduled-tasks.ts:179-183`) — an additive change to the shared primitive, chosen over post-insert `updateTask` re-merge because the two-step variant leaves a window where an imminent-`process_after` row could fire scriptless. Existing callers are unaffected (field optional).
- **Schedule preservation:** target row keeps the source's `process_after` (no recompute). Imminent-fire edge: source is already cancelled by step 3, so a due-now target fires once at the preserved slot — no double-fire, no missed fire.
- **Cancel-first rationale:** cancel-first's failure mode (brief gap, recoverable from the in-memory snapshot) beats insert-first's (double-fire — the incident class this feature exists to prevent). Both writes are local SQLite; the compensation window is milliseconds.

### 4.3 Cancel provenance & distinguishability

`cancelTask` marks rows `completed` (C1 forbids new status values). Distinguishability comes from the **audit table** (§4.4), not a content stamp: history rendering joins `scheduled_audit` on `(series_id, action='cancel')` to label board-cancellations. (rev 2: the rev-1 content-stamp design cited `updateTask` for a `_cancelled` merge it cannot perform — `db.ts:96-98` whitelists `prompt`/`script` only.)
**Resurrection guard (rev 3):** board cancel ALSO clears `recurrence` on the series' terminal rows — crash residue (`recurrence.ts:36-37` insert-then-clear) or a swallowed-parse strand can leave a terminal row recurrence-set, which `getCompletedRecurring` (`db.ts:143-146`) would heal into a fresh successor, silently undoing the cancel. Clearing it is a data operation through the existing recurrence-clear pattern in service of explicit operator intent; it removes rows from the sweep's input but changes no firing-path code (noted against C1 deliberately).

### 4.4 Provenance (audit) — minimal table, hashed bodies

The brief's "minimal provenance, full audit table out of scope" intent is honored as: **one table, no UI beyond the drawer tail, no retention machinery beyond a sweep prune** — adopted because the brief's assumed alternative (content stamping) is mechanically impossible (§4.3). ⚠️ **Flagged as a brief amendment for operator approval at the design gate.**
```sql
CREATE TABLE scheduled_audit (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  ts TEXT NOT NULL DEFAULT (datetime('now')),
  actor TEXT NOT NULL, action TEXT NOT NULL,        -- edit|pause|resume|run_now|cancel|move
  agent_group_id TEXT NOT NULL, session_id TEXT NOT NULL, series_id TEXT NOT NULL,
  before_hash TEXT, after_hash TEXT,                -- sha256 (steer.ts:17 createHash precedent)
  before_preview TEXT, after_preview TEXT,          -- prompt first 512 chars; scripts hash-only, never verbatim
  before_len INTEGER, after_len INTEGER,
  detail_json TEXT,                                  -- non-body fields: cron change, move source→target,
                                                     -- secret-delta COUNTS + hashes ONLY (names are never
                                                     -- persisted — persisting them would re-open the
                                                     -- enumeration hole §4.5 closes at preview)
  resolved_at TEXT                                   -- move_intent rows only; see §4.2 step 2b
);
```
Central-DB migration. Move rows are keyed to BOTH groups (one row per side, shared correlation id) so each side's audit tail is complete without cross-scope reads. The audit tail inside the detail response is served at mutation tier only (read-tier detail omits it). Retention: at 90 days the sweep prunes `before_preview`/`after_preview`/`detail_json` bodies ONLY — action metadata rows (actor/action/ts/hashes) are kept for the series' lifetime, so cancel-vs-completed distinguishability survives pruning. Verbatim prompt/script bodies are never persisted (no second long-lived plaintext copy of unattended-execution code).

### 4.5 Authorization

- Shared gate `canManageScheduled(userId)` = owner ∥ global-admin (D7, strictest tier v1), called by **every mutation handler AND `move/preview`** — preview reads vault secret names and is gated at mutation tier, not read tier (closes the scoped-admin secret-name enumeration hole; `targetAgentGroupId` is attacker-supplied body input the read filter never sees). "Owner"/"global-admin" are the GLOBAL `user_roles` tiers (`steer.ts` `isOwner`/`isGlobalAdmin`) — global authority makes a source-vs-target split vacuous at this tier; revisit only with a future scoped-admin mutation tier (W1).
- **Cron edits recompute the live row's `process_after`** via the canonical parse below (same mechanism as resume §4.7) — `updateTask` alone leaves the old slot in place (`db.ts:104-110`) and the board would display the new cron while the next fire follows the old one.
- **Rate limiting:** steer's per-user limiter (`steer.ts` rateLimitMap precedent) applies to `run-now` and `move` — the two verbs that convert a keypress into container compute.
- **No authz decision is ever made from the decoded `:key` alone** — every verb re-resolves the agent group from the key and re-checks scope server-side at call time.
- Read handlers (list, detail, history) apply the standard scope filter (C7) with disclose-as-not-found.
- Module-owned detection: series-prefix registry (`memory-synth-*`, `memory-lint-*`) + static map for mnemon/support series → `{moduleOwned, owner}` in the payload.
- Input bounds: prompt ≤ 8000 chars, script ≤ 4000 chars; edits flow through `updateTask`'s object-merge path (JSON.parse → property-set → stringify, injection-safe per `db.ts:95-98`) — never string-splice into content.
- Cron validation: `CronExpressionParser.parse(cron, { tz: TIMEZONE })` — byte-identical call to `recurrence.ts:31` — plus `.next()` twice to confirm a finite interval; reject on throw with the parser's message (divergent-acceptance would create silently-dead series, the exact failure the board exists to catch).
- SSE: board-relevant emits always set `agent_group_id` to the task's owning group (never null — null would bypass `_scopeAllows` per-group filtering for that frame). **Coverage (rev 3):** verified emit sites cover inbound writes + outbound delivery only — neither `handleRecurrence`'s successor insert nor `scheduleTask` emits, and the InboxBoard precedent runs `refreshInterval: 0` (`InboxBoard.tsx:76`), so SSE alone leaves the board stale across fire/recovery transitions. Board mutation handlers emit `session_event`; the scheduled view additionally polls with `refreshInterval: 45_000` as the real freshness backstop.

### 4.6 Run-now

`updateTask(processAfter = now)` on the live row, then `wakeContainer(session)` — fires in seconds. Guard: if `processing_ack` shows the row claimed (best-effort read, §4.1) or `process_after ≤ now` already → 409 `{reason}`. Recurrence advances normally on completion (`recurrence.ts:31-37` computes next from *now* — an early fire does not shift the schedule). **Near-slot edge (documented):** run-now shortly before the scheduled slot fires twice minutes apart (early fire completes → next-after-now = the imminent slot); the UI confirm warns when `now` is within one grace window of the next slot.

### 4.7 Resume semantics

`resumeTask` flips paused→pending but leaves stale `process_after` (immediate-replay — rejected by brief D3). Board's resume: recompute `process_after` via the §4.5 canonical parse (`.next()` is implicitly after-now = the skip semantic) using `updateTask` (matches paused rows, `db.ts:81`), *then* `resumeTask`.

### 4.8 Session-DB index (read-path enabler)

`messages_in` has only `idx_messages_in_series (series_id)` (`src/db/schema.ts:192`) — `MAX(seq)` and `ORDER BY seq DESC LIMIT 5` both materialize + sort all series rows. Add to BOTH the baseline `INBOUND_SCHEMA` and the `migrateMessagesInTable` function (`session-db.ts:444`, called from the write-path open at `session-manager.ts:606` — board read-only opens cannot create it; dormant sessions get it on next write-open, and board reads tolerate its absence by falling back to the scan):
```sql
CREATE INDEX IF NOT EXISTS idx_messages_in_series_seq ON messages_in(series_id, seq DESC);
```
Read-path only; C1 semantics untouched.

### 4.9 Event-loop discipline

better-sqlite3 is synchronous; the assembly must never run as one contiguous block in a request handler (it would stall delivery polls and SSE writes in the shared host process). §3a's `setImmediate`-per-session chunking + single-flight promise + 5s TTL is the chosen mechanism. busy_timeout 1000ms on all board opens bounds any lock-hold against container writers (outbound.db) — structurally identical to the existing delivery-poll read pattern.

## 5. MVP Scope Boundary (normative)

**IN (v1):** nine routes (§3b); health derivation incl. residual-strand + duplicate-successor detection; grouped-list UI with strip/drawer/filters/search; edit prompt/script/cron (validated, bounded); pause/resume (slot-recompute); run-now (wake + 409 guard); cancel (audit-labeled); move (preview/execute, delta re-check, compensation, invariant check, `TaskDef.script` extension); module-owned badges + confirm; thread-loop badge (pause/resume/cancel; move disabled — resume recompute §4.7 applies to thread rows too); `scheduled_audit` table + migration + 90d prune; `(series_id, seq DESC)` index migration; owner/global-admin gate incl. preview; SSE `session_event` reuse; RouteNav third entry.

**OUT (v2+):** create-from-board (D3); alerting (non-goal); moving thread-scoped loops (D9); **moving one-off tasks** (TaskDef.cron type hole — §4.2); central-table migration (D1); dedicated `scheduled_event` SSE type (45s poll + mutation emits suffice); skipped-vs-quiet fire disambiguation (needs a fire-outcome record the firing path doesn't write — would violate C1); **move config-delta preview beyond secrets** (§4.2 preview caveat); per-series grace overrides; mobile drawer editing (read-only v1).
