## MUST-FIX Findings

### [M1] Two sources of truth for workgroup membership (filesystem vs DB)

- **Raised by:** Reviewer A (#2), Reviewer C (#1)
- **Finding:** Design § "Mnemon `'workgroup'` mode" specifies the resolver walks container.json files (matches existing `getAllMemoryEnabledGroupIds` at `scope-resolver.ts:40`). Design § "Recommendation" specifies projection uses `WHERE agent_group_id IN (SELECT id FROM agent_groups WHERE workgroup_id = ?)` — i.e. DB-driven. **The design rejected Option B precisely to avoid filesystem-vs-DB drift, then re-introduces it.** If an operator edits `container.json.workgroup_id` and the DB column lags, recall and projection target different membership sets.
- **Effort to Fix:** Low — pick one canonical source.
- **Impact if Ignored:** High — the design's stated isolation boundary (C1) becomes ambiguous under drift; recall could widen beyond what the projection contains, returning thread IDs that `read_thread` then can't load.
- **Suggested resolution:** Make `scope-resolver.ts` read `workgroup_id` from `agent_groups` in the central DB (host has DB access via the same `data/v2.db` mount that the projection builder uses). Container.json declares operator intent; DB is canonical for runtime queries. Add a host-side reconciler that updates the DB column whenever container.json changes — explicit pseudocode in the design (also addresses M9).
- **Fact-check:** Verified — `scope-resolver.ts:30-66` shows pure filesystem reads; projection at `per-agent-projections.ts:104` uses DB query. Both are correct in isolation; combined they create the drift surface.
- **Status:** Open

### [M2] Workgroup-of-1 identifier inconsistent across design ("own id" vs "own folder name")

- **Raised by:** Reviewer A (#3)
- **Finding:** The design specifies the standalone identifier in three places with two different values:
  - Recommendation § "Mnemon default scope flip": "workgroup_id = own id → workgroup-of-1 → same row set as 'self'"
  - Sub-decisions § "Backfill heuristic": "Standalone (no match) → workgroup_id = own folder name"
  - Decision D6 description: "Standalone (no match) → workgroup_id = own folder."

  `agent_groups.id` (`ag-<timestamp>-<rand>`) and `agent_groups.folder` (human slug like `axie-dev`) are distinct columns. Migration backfill SQL is unclear which to use.
- **Effort to Fix:** Low — pick one, propagate.
- **Impact if Ignored:** High — backfill would set workgroup_id to whichever the implementer happened to read; projection `WHERE workgroup_id = ?` queries with the wrong handle return empty; foreign key (M3) can't be enforced if the column carries mixed values.
- **Suggested resolution:** Use `agent_groups.folder` (human-readable slug) as `workgroup_id` and `workgroups.id`. Rationale: operator-facing (carries display meaning), `folder UNIQUE` constraint makes the namespace clean, container.json declarations match what operators see. Standalone groups: `workgroup_id = folder`. Backfill: `<x>-codex` rows get `workgroup_id = <x>`.
- **Fact-check:** Verified — `agent_groups.id` is the timestamp-rand form (migration 001), `agent_groups.folder TEXT NOT NULL UNIQUE` is the slug column.
- **Status:** Open

### [M3] No FOREIGN KEY on `agent_groups.workgroup_id` → `workgroups(id)`

- **Raised by:** Reviewer A (#4)
- **Finding:** Design § "Option A approach" specifies `workgroup_id TEXT` but does not specify a FK constraint. Migration 001 uses FK references extensively (e.g. `REFERENCES agent_groups(id)`). Without a FK, a typo or stale container.json silently produces an orphan `workgroup_id` pointing at no `workgroups` row.
- **Effort to Fix:** Low — add `REFERENCES workgroups(id)` to the column definition.
- **Impact if Ignored:** Medium — projection's `IN (SELECT id FROM agent_groups WHERE workgroup_id = ?)` still returns a useful set (the orphan agent itself), but OneCLI secret inheritance reads `workgroups(id) JOIN` → no row → no inherited secrets. Silent under-credentialing.
- **Suggested resolution:** Declare `workgroup_id TEXT NOT NULL REFERENCES workgroups(id)`. Migration UP must `INSERT INTO workgroups` before `UPDATE agent_groups SET workgroup_id` to satisfy FK. Reconciler on spawn also inserts the workgroups row before updating the column (transaction).
- **Fact-check:** Verified — `migration001.ts` uses `REFERENCES` for several FKs; SQLite supports it.
- **Status:** Open

### [M4] Pooled `messages_archive` projection contains duplicate inbound user rows (one per sibling agent)

- **Raised by:** Reviewer A (#5)
- **Finding:** When `<x>` and `<x>-codex` are wired to the same channel, both receive every inbound user message (per `src/router.ts:793, 916, 932` — each agent gets its own archive row via `messageIdForAgent(event.message.id, agent.agent_group_id)`). Today's per-agent projection filters to one `agent_group_id` so the duplicate is invisible. With pooled workgroup projection, **every user message appears N times** in the projection.
- **Effort to Fix:** Medium — design must pick a dedup strategy.
- **Impact if Ignored:** High — `search_threads` BM25 ranking double-counts matches and surfaces duplicate-heavy threads as more relevant; `read_thread` transcript shows the user's message N times in chronological order; `resolve_thread_link` transcript is N× expected length. This is a user-visible quality regression that violates R2 (siblings can read each other's chat archive "via existing tools — no API change").
- **Suggested resolution:** Dedup in the projection. Two options:
  - **(a)** Canonical row: `SELECT * FROM messages_archive WHERE agent_group_id IN (?) GROUP BY <dedup_key>` where dedup_key is `(messaging_group_id, thread_id, sent_at, role, text)` — keep the row with the lowest `agent_group_id` (deterministic).
  - **(b)** Insert-time dedup: when `messageIdForAgent` writes the N-th row, check if a row with the same dedup_key already exists for any workgroup member and skip. More invasive; touches `message-archive.ts`.

  Recommend (a) — projection-only change, no archive write-path edits. Tests assert the dedup behavior.
- **Fact-check:** Verified — `router.ts:793, 916, 932` all call `messageIdForAgent(event.message.id, agent.agent_group_id)` (produces distinct row ids per agent).
- **Status:** Open

### [M5] Per-table pooling strategy unspecified for central projection (backlog, ship_log, tasks, capabilities)

- **Raised by:** Reviewer A (#6, #14), Reviewer C (#5)
- **Finding:** Design § "MVP Scope IN" says "filter on `workgroup_id` via join (for `backlog_items`, `ship_log`)" but `buildCentralProjection` (`per-agent-projections.ts:143-150`) copies four tables: `backlog_items`, `ship_log`, `tasks`, `agent_group_capabilities`. The design doesn't decide pool-vs-isolate per table. **`agent_group_capabilities` pooled would be a real bug** — the orchestrator capability check (`container/agent-runner/src/mcp-tools/server.ts:45`) would return true for any workgroup member if ANY member is orchestrator-capable. Verified: `grep` shows 9 in-container `WHERE agent_group_id = ?` filter sites across `thread-search.ts` (3), `backlog.ts` (5), `server.ts` (1) — design only addresses thread-search.
- **Effort to Fix:** Medium — explicit per-table table in the design.
- **Impact if Ignored:** High — orchestrator role silently pools across siblings (security/capability invariant violation); backlog and ship_log have a partial-pool semantic (projection contains workgroup rows but in-container filter narrows to self, doubling disk usage with no functional benefit).
- **Suggested resolution:** Explicit per-table strategy:

  | Table | Pool to workgroup? | In-container filter? | Rationale |
  |---|---|---|---|
  | `messages_archive` | YES | DROP | siblings share chat history (the brief's R2) |
  | `backlog_items` | NO (stay agent-scoped) | KEEP | each agent has its own todo list |
  | `ship_log` | NO | KEEP | each agent's commits are its own activity |
  | `tasks` | NO (filter by `parent_agent_group_id` stays) | KEEP | dispatch ownership is per-agent |
  | `agent_group_capabilities` | NO | KEEP | orchestrator role is per-agent |

  Update `buildCentralProjection` to accept per-table filter columns (already structured this way at `per-agent-projections.ts:145-150`) — leave the existing logic intact for the four central tables. Only `messages_archive` gets workgroup widening.
- **Fact-check:** Verified — `server.ts:45` orchestrator check, `backlog.ts:273-342` (5 sites). All 9 in-container filter sites enumerated above.
- **Status:** Open

### [M6] Mnemon store routing semantics unspecified — fan-out vs single-store-per-workgroup

- **Raised by:** Reviewer A (#8, #9)
- **Finding:** Design § "Mnemon `'workgroup'` mode" says recall walks containers and "filters where workgroup_id equals the calling group's workgroup_id". `mnemon-impl.ts:225-279` already does multi-store fan-out (one `mnemon recall --store <agentGroupId>` per group id). Combined with the existing `MNEMON_STORE_<folder>` env override (which redirects codex twin's MNEMON_STORE to the parent's store), the design produces ambiguous read paths: the env override redirects twin reads to parent's store, AND the workgroup fan-out queries both stores — overlap, double latency, no dedup analysis.
- **Effort to Fix:** Medium — pick approach and document.
- **Impact if Ignored:** Medium — pooling works but with read-path redundancy and unclear write semantics for future fresh installs where the codex twin's store could accumulate facts.
- **Suggested resolution:** Single mnemon store per workgroup. `workgroups.id` IS the store name (or carry a `mnemon_store_id` column on workgroups for explicit decoupling). All members read/write the same store. Subsumes the `MNEMON_STORE_<folder>` env override (makes it dead code, but the env override stays in place for the transition per C6). Scope-resolver returns `[workgroups.mnemon_store_id]` (single id) for workgroup mode — fan-out collapses to a single store call.
- **Fact-check:** Verified — `mnemon-impl.ts:225-279` does fan-out; `container-runner.ts:1773-1779` env override is unchanged.
- **Status:** Open

### [M8] Default-flip for `getRecallScope` is a behavior change shipped in the same migration as the schema change

- **Raised by:** Reviewer B, Reviewer C (#4)
- **Finding:** Design § "Mnemon default scope flip" changes `getRecallScope` default from `'self'` to `'workgroup'` at `container-config.ts:74`. Best practice for behavior-changing defaults (PlanetScale, Fowler expand-and-contract, Shopify) is to ship the schema change first and flip the default in a follow-on after operator confirmation. The current design ships both in one migration. For a personal install this is defensible but conflates "structural change" with "user-facing behavior change".
- **Effort to Fix:** Low — change approach.
- **Impact if Ignored:** Medium — any existing group with `memory.enabled: true` and no explicit `recall_scope` silently moves from `'self'` to pooled-workgroup recall. For sibling pairs that's the intended outcome; for standalone groups the behavior is identical (workgroup-of-1); for groups that depended on implicit `'self'` it's a surprise.
- **Suggested resolution:** Keep the `getRecallScope` default at `'self'`. During migration, write `recall_scope: 'workgroup'` explicitly into the `memory` block of every auto-paired group's `container.json` (those with non-singleton workgroups). Standalone groups untouched. Net behavior matches the default-flip outcome but with no surprise change to implicit-self consumers.
- **Fact-check:** Verified — `container-config.ts:73-75` returns `'self'` as default; `recall-injection.ts:14` imports and uses `getRecallScope` unconditionally.
- **Status:** Open

### [M9] Invalid/orphan/NULL `workgroup_id` behavior unspecified (fail-closed semantics)

- **Raised by:** Reviewer C (#2)
- **Finding:** Design does not specify what happens when:
  - `agent_groups.workgroup_id` is NULL (post-migration mistake or new group inserted without it)
  - `agent_groups.workgroup_id` references a nonexistent `workgroups.id` (FK absent per M3, or row deleted)
  - Backfill fails to assign a workgroup_id to some rows
- **Effort to Fix:** Low — write the invariants explicitly.
- **Impact if Ignored:** Medium — silent failure modes when invariants violated; the workgroup boundary IS the security boundary per C1, so silent fallback is dangerous.
- **Suggested resolution:** Explicit invariants section in design:
  - **Invariant W1:** Every `agent_groups` row has a non-null `workgroup_id` (enforce via `NOT NULL` constraint after backfill).
  - **Invariant W2:** Every `agent_groups.workgroup_id` references an existing `workgroups.id` (FK enforces, per M3).
  - **Invariant W3:** Projection build fails closed if the spawning agent has invalid workgroup_id (NULL or FK violation) — `buildArchiveProjection` throws an explicit error rather than producing an empty or self-only projection.
  - **Migration validation:** before `schema_version` is recorded, assert all rows pass W1 and W2.
- **Fact-check:** Verified — current `buildArchiveProjection` at `per-agent-projections.ts:89-121` handles missing source files but doesn't validate scoping invariants.
- **Status:** Open

### [S6] OneCLI workgroup-secret validation at row-write time

- **Raised by:** Reviewer A (#15)
- **Finding:** `applyOnecliSecrets` hard-fails on unresolvable names (`onecli-secrets.ts:156-162`). A bad workgroup-level secret name would kill every member's spawn.
- **Suggested resolution:** Validate the secret list when writing to `workgroups.onecli_secrets` (resolve UUIDs eagerly; reject the write if any fail). Cache resolved UUIDs on the row. Spawn-time resolution is a fast path lookup.
- **Status:** Open

### [S7] Backfill report-and-confirm output

- **Raised by:** Reviewer B
- **Finding:** Best practice for heuristic backfill: explicit report of decisions made, rows not matched, potential false-pairs caught.
- **Suggested resolution:** Migration UP emits a structured log: pairs found, rows defaulted to standalone, suffix-strip candidates that failed parent-existence check.
- **Status:** Open

### [S8] Structural test for projection chokepoint

- **Raised by:** Reviewer B
- **Finding:** Removing the in-container filter makes the projection the sole enforcement point. AWS prescriptive guidance flags this exact failure mode (new query paths added later that bypass the chokepoint).
- **Suggested resolution:** Add a structural test (vitest) that greps `container/agent-runner/src/mcp-tools/` for `messages_archive` queries that don't go through the helper, and fails if any are found.
- **Status:** Open

### [S9] Single-transaction migration (schema + backfill + version bump)

- **Raised by:** Reviewer C (#3)
- **Finding:** Schema-version gating alone doesn't guarantee idempotency under partial failure. Backfill mid-failure could leave rows un-assigned but schema_version unbumped → re-run hits "column already exists" errors.
- **Suggested resolution:** Wrap migration 036 in a single SQLite transaction (BEGIN/COMMIT). Use `IF NOT EXISTS` for `ALTER TABLE` and `CREATE TABLE`. UPDATE is naturally idempotent. Bump schema_version only after backfill validation passes.
- **Status:** Open

### [S10] Migration report of duplicate per-group secrets eligible for consolidation

- **Raised by:** Reviewer C (#6)
- **Finding:** Existing per-group `onecliSecrets` declarations across sibling container.json files often duplicate the future workgroup-level list. Design doesn't surface them for operator action.
- **Suggested resolution:** Migration emits a report listing per-workgroup intersection of member secrets — operator can review and move common items to `workgroups.onecli_secrets`. Tooling is out of scope per the brief; report is in scope.
- **Status:** Open
