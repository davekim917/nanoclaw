## Summary

Bring **OpenCode** to parity with Claude/Codex on command guards, and make all three fail closed by construction. **Correction (A5, verified runner.ts:21-24,244-250):** Claude AND Codex already share self-approval / snowflake / email-gate / git-clone — Codex inherits them by importing the `claude.ts` hook factories. **Only OpenCode is blind.** So this feature is: (1) give OpenCode the four guards it lacks by routing it through the shared core; (2) extract the policy of those guards into the core **without breaking the `claude.ts`→codex-runner import chain** (new HARD invariant, below); (3) add OpenCode tool-access parity + fail-closed + env/secret parity; (4) bring **Codex's runner to fail-closed** to honor C4; (5) move clones to the shared workgroup; (6) pin it with a table-driven dispatch-coverage seam. Spans `nanoclaw-v2/container/agent-runner` + `davekim917/bootstrap/plugins/workflow` (vendored to `workflow-agents` via `vendor-guards.mjs`).

## Component Designs

### D-A · email-gate → pure evaluator (verdict shared; approval I/O per-adapter)
**Chosen:** New vendored `email-gate-core.ts` exporting `evaluateEmailSend(command, envSnapshot) → { action: 'allow' | 'gate'; label?; summary?; reason? }` — pure (envelope parse relocated from claude.ts:543-664). **`EnvSnapshot = { isScheduledTask: boolean }`** only (S3/A6 fix: the GWS creds account is parsed from the *command* string at claude.ts:642-643, not an env var — the evaluator parses it from `command` itself). The **verdict** (allow vs gate) + the **card content** (`label`/`summary`) are shared, so the approval request can't silently degrade across adapters (S5). The approval **round-trip** is per-adapter and must emit the **same `request_bash_gate` action + 60-min timeout + fail-closed-on-deny/timeout** as Claude/Codex. **Correction (C3-1 / A-Finding-2, verified block-destructive-core.ts:963):** the sync `writeGateRequest` currently **hardcodes `action: 'request_destructive_gate'`** (host routes that to a "🛑 Destructive command" card vs bash-gate's "⚠️ Bash command" — src/modules/bash-gate/index.ts:293-310). So OpenCode's email gate must NOT reuse it as-is. **As-built call chain (cycle-4 A-Finding-2, verified):** `writeGateRequest(label, summary, command)` is **positional** (block-destructive-core.ts:951-955), and is called **only** by `runNanoclawGate(command, reason, onStageError?)` at :1063 (`writeGateRequest(reason, reason, command)`) — adapters never call `writeGateRequest` directly; they call `runNanoclawGate`, which is **today's destructive wrapper** (invoked by OpenCode at opencode-guard.ts:78 and Codex at runner.ts:153). Fix (cycle-5 codex-C5-1 — signature-safe): **do NOT insert `action` positionally into `runNanoclawGate`** — its current signature is `runNanoclawGate(command, reason, onStageError?)` and existing callers pass the callback as **arg 3** (Codex runner.ts:153 `runNanoclawGate(command, reason, () => {…})`, OpenCode opencode-guard.ts:78, Claude block-destructive); inserting `action` at position 3 would shift the callback and regress the destructive gate (a parity regression in the very primitive this feature unifies). Instead: add an `action` parameter to the internal `writeGateRequest` (called only by the gate wrappers, so its signature is free to change), add a new **action-aware lower-level API `runGateRequest(command, reason, { action, onStageError })`**, and keep the **existing `runNanoclawGate(command, reason, onStageError?)` signature unchanged** as the destructive wrapper over `runGateRequest` (action `request_destructive_gate`). `runEmailGate(command, reason, onStageError?)` is the bash-gate wrapper (action `request_bash_gate`). A **regression test asserts the legacy 3-arg `runNanoclawGate(cmd, reason, cb)` call still emits `request_destructive_gate`** (no caller churn). OpenCode email calls `runEmailGate`→`pollDeliveredTable` (block-destructive-core.ts:1016-1041). Claude/Codex keep async `writeMessageOut`+`awaitDeliveryAck` (claude.ts:668-702, already `request_bash_gate` at :681) — **untouched (C3)**. A dispatch test asserts email→`request_bash_gate`, destructive→`request_destructive_gate` per adapter (this build-time assertion is what gates the C2 "stale primitive" failure mode; the D-E export-validation is the runtime defense-in-depth on top).

*Options:* (A) pure evaluator in shared core **[chosen]**; (B) inline-only — rejected (OpenCode can't reach); (C) parse-only extract — rejected (doesn't solve parity). **Confidence: Medium-High.**

### D-B · approval gate primitive — OpenCode reuses the sync Bun gate (code reuse)
**Chosen:** OpenCode uses the sync `runNanoclawGate`/`writeGateRequest`+`pollDeliveredTable`; Claude/Codex keep async `awaitDeliveryAck`. **Rationale (S1/A1 correction):** OpenCode's `tool.execute.before` IS `async` and *can* `await` (opencode-guard.ts:99; OpenCode plugin docs) — so this is **not** forced by a contract limit. OpenCode uses the sync path because `runNanoclawGate` already exists in the core, OpenCode runs on Bun (`Atomics.wait` works), and `gateBashOrThrow` is already a sync throw it reuses for the destructive gate. It's deliberate **code reuse**, not a limitation. (A future maintainer MAY unify on the async path; nothing blocks it.)

*Options:* (1) reuse sync Bun gate **[chosen, code-reuse]**; (2) unify async + sync-wrapper — viable but no current gain; (3) async everywhere — viable later. **Confidence: High.**

### D-C · self-approval + snowflake → pure evaluators; preserve the codex import chain
**Chosen:** Extract `evaluateSelfApproval` (`SELF_APPROVAL_RE`, claude.ts:470-484) + `evaluateSnowflakeConnector` (`SNOWFLAKE_CONNECTOR_EXEC_RE`, claude.ts:498-512) into `block-destructive-core.ts` (extend; no `VENDORED_FILES` change), returning `{action:'allow'|'block', reason?}`. **The existing `claude.ts` hook factories (`createSelfApprovalBlockHook`, `createBlockSnowflakeConnectorHook`, `createEmailGateHook`) MUST keep their signatures** — the codex runner imports and calls them (runner.ts:21-24, 244-250). Refactor their *bodies* to delegate to the new evaluators (thin verdict→`denyBash`, fail-closed fallback); do NOT remove/rename the factories (HARD invariant). `opencode-guard.ts` calls the evaluators directly in its chain. **sanitize-bash** stays a command **transform** (claude.ts:431-449); its secret-stripping effect reaches OpenCode via D-E env-scrub.

*Options:* extend `block-destructive-core.ts` **[chosen]**. **Confidence: High.**

### D-D · OpenCode tool-access parity (reframed — M2 + M3, simplified per cycle-3 A-Finding-1)
**M3 (verified):** the 9 `SDK_DISALLOWED_TOOLS` are Claude-Code CamelCase builtins (claude.ts:114-124); OpenCode's tools are lowercase domain tools (`bash`/`edit`/`write`) + `mcp__server__tool` (mcp-to-opencode.ts:26-51). **OpenCode does not expose those 9 names** — verified end-to-end (A cycle-3). So:
- **The denylist stays SINGLE-SOURCE in nanoclaw** — `SDK_DISALLOWED_TOOLS` (claude.ts:114-124), consumed by Claude (the sync `disallowedTools` SDK arg at claude.ts:1290 + `preToolUseHook` at :236-244) and by Codex via the **same-repo** re-export (runner.ts:358). That's already trivially consistent (one symbol, one repo). **No cross-repo copy, no byte-equal cross-repo test** — `SDK_DISALLOWED_TOOLS` does not and need not exist in the bootstrap repo (the two are isolated Bun trees; vendor-guards reaches one way only). *(M2's cycle-2 "duplicate across the repo boundary + byte-equal parity test" was unimplementable AND unnecessary — dropped.)*
- **OpenCode parity = absence + a RECURRING build-time enumeration test** (not a one-time snapshot — B-LOW2): the test enumerates OpenCode's exposed tool inventory (built-ins + `mcp__` tools) and classifies each against a **minimal capability map** (C3-3): every exposed tool must map to *known-safe* or *blocked-equivalent*; the test **fails on any denied-capability match OR any unrecognized tool**, so the inventory can't rot silently as OpenCode evolves. (The full capability-normalization layer remains deferred — N3 — but this minimal classify-or-fail map is IN, so "denied capability" is concrete.)
- **No runtime denylist check is added to `opencode-guard.ts`** — for the current OpenCode tool surface it would be a pure no-op (the 9 names can't occur). If a future enumeration finds a real OpenCode equivalent, *that* gets an explicit block then. (This removes the D-G "test a real OpenCode tool name through the production denylist" contradiction — codex C3-2 — there is no production OpenCode denylist to test.)
- **Why this is parity, not a gap (cycle-4 C1):** the 9 denied names are Claude-Code **CLI builtins** (Cron*, ScheduleWakeup, AskUserQuestion, Enter/Exit PlanMode, Enter/Exit Worktree) — runtime-harness features with **no OpenCode analog and no arbitrary-MCP analog** (the denylist matches by exact tool name, so a hypothetical `mcp__x__create_cron` is not on it for *either* runtime). The **substantive dangerous-capability gating** (bash `rm`/destructive, `.env`/lockfile/`.git` edits via file-protection, email-send, snowflake-connector, git-clone) is the **other guards — all of which already run on OpenCode** via `tool.execute.before` (D-A/D-C/D-E). So denylist "parity" means *neither runtime exposes those builtin names*; it is not the layer that gates dangerous capabilities. C1's provider-neutral **runtime** capability-normalization gate is the deferred **N3** hardening (MVP-OUT) — adding it now expands scope past the MVP boundary; the recurring enumeration test (above) is the build-time net that fires if OpenCode ever does expose a denied-equivalent.

*Options:* (1) single-source nanoclaw denylist + OpenCode absence + recurring enumeration **[chosen]**; (2) cross-repo copy + byte-equal test — rejected (unimplementable + unnecessary, A-Finding-1); (3) permission-event check — rejected (SDK may not expose `tool_name`); (4) MCP config-time filter — rejected (misses built-ins). **Confidence: Medium-High** (rests on the recurring enumeration test being wired into CI).

### D-E · fail-closed (BOTH OpenCode and Codex) + env/secret parity
**M4 correction:** C4 is violated by *two* adapters today, not one. Fix both:
- **OpenCode:** `buildOpenCodeConfig` throws if `!guardAvailable` (opencode.ts:332-342) instead of warn-and-continue. Additionally, on load, assert the guard module exports the symbols OpenCode actually consumes **— both the verdict evaluators AND the gate primitives** (`evaluateEmailSend`, `evaluateSelfApproval`, `evaluateSnowflakeConnector`, `evaluateGitCloneDestination`, **plus the parameterized `writeGateRequest` / `runEmailGate` / `runNanoclawGate` / `pollDeliveredTable` the email round-trip depends on**) and fail closed if any is missing OR has the wrong type (codex-C4 / cycle-4 C2: "present ≠ correct" must cover the approval primitive, not just the evaluators — otherwise OpenCode can appear guarded while the email gate is stale/hardcoded to `request_destructive_gate`). *(Not the denylist — per D-D, OpenCode consumes no denylist.)*
- **Codex (BOTH dynamically-loaded cores — cycle-4 M1, verified):** today Codex has **two** fail-open paths, not one — `loadGuardCore`/`runDestructiveGuard` (runner.ts:106-116/138-139, `if (!core) return null // fail-open`) **and** `loadFileProtectionCore`/`runFileProtection` (runner.ts:178-186/195-196, `return null // fail-open: file-protection unavailable`). D-E flips **both** to **fail closed** (deny) to honor C4 and match the design's own "uniform fail-closed" claim (D-G). **"Invalid core" must be handled, not just "missing" (cycle-4 C3):** a malformed-but-importable core passes the bare `await import()` then throws at call time (`core.evaluateBashCommand` runner.ts:141 / `core.checkEditProtection` runner.ts:197) outside any deny path. So each loader must **validate the required exports' types** (typed-failure → deny) AND `runDestructiveGuard`/`runFileProtection` must **map any evaluator exception to a deny decision**. Tests cover missing / malformed / throwing for each core. **Scope clarification (A-Finding-4):** these two loaders are the container-side cores Codex loads dynamically — SEPARATE from the four `claude.ts` hook factories (self-approval/snowflake/git-clone/email-gate) that the codex chain imports and runs at runner.ts:244-250 *regardless* (same-repo imports — they cannot be "absent"). So the flip changes Codex behavior only when a **mounted core** is absent/malformed; it does not alter the four migrated guards' Codex behavior. The mount is an always-present invariant on this fleet, so fail-closed never wedges in practice; the deliberate fail-open comments are superseded by C4. *(Auto-judgment recorded — honors HARD C4 + the parity mandate; strengthens safety; the more conservative option; completes the design's own "fix BOTH adapters" goal.)*
- **Claude** already fails to a closed inline path — the git-clone hook denies on any non-`allow`/thrown evaluator (claude.ts:760-761) with the inline-regex fallback (claude.ts:768-773) — unchanged. *(citation corrected per A-Finding-3.)*
**Env (C12):** before `spawnOpencodeServer` (opencode.ts:102-107) strip the auth env vars (`buildSecretEnvVarList`, claude.ts:422-429) from the child env — safe (OpenCode auths via auth.json/XDG, opencode.ts:52). Note this strips for the **whole OpenCode session** (broader/earlier than Claude's per-command `unset`, A12) — same security outcome for shell subprocesses.

*Options (fail-closed):* (A) refuse spawn / fail-closed **[chosen, both adapters]**; (B) deny-by-default — rejected; (C) `OPENCODE_ALLOW_UNGUARDED=1` dev opt-out — additive, default-closed. **Confidence: Medium** (Codex fail-closed flip is the watch item).

### D-F · clone destination → shared workgroup (citation + fallback fixes)
**Chosen:** runtime `getReposDir()` leads with **`fs.existsSync('/workspace/workgroup')`** (the load-bearing check; `NANOCLAW_WORKGROUP_ID` is decorative given the dir gate — A8) → `/workspace/workgroup/repos`, else `/workspace/agent/repos`. **S6/C5:** if `NANOCLAW_WORKGROUP_ID` is set (workgroup *expected*) but `/workspace/workgroup` is absent → that's a mount failure: **warn loudly / error, do NOT silently clone private.** `resolveRepoDir` precedence workgroup/repos → agent/repos → legacy agent/<name>; on a same-name repo present in two locations, **prefer + warn (origin-match)**, don't silently shadow. `clone_repo`: verify `git config --get-url origin` matches the requested URL before reuse. **S7/A9:** the "only `rmSync` an empty no-`.git` dir" change is an *intentional behavior change* (today it clears ANY no-`.git` dir incl. non-empty, git-worktrees.ts:221-223) — for a non-empty no-`.git` dir, return an error (don't destroy). **M1 fix:** add `/workspace/workgroup` to `SEND_FILE_ALLOWED_PREFIXES` (core.ts:23-28) **and `FILE_EVENT_ALLOWED_PREFIXES` at poll-loop.ts:74-80** (corrected from the wrong :48-49). `WORKTREES_DIR` unchanged.

*Options:* (A) runtime `getReposDir()` **[chosen]**; (B) module-init const; (C) clone-to-agent + resolve-reads-workgroup — rejected (doesn't share on clone). **Confidence: High.**

### D-G · conformance seam — table-driven dispatch coverage (S8/M3/M4)
**Chosen:** `conformance.test.ts` pins core **verdicts**; per-adapter **dispatch-coverage tests** drive each adapter's REAL entrypoint **table-driven over every migrated command-guard** (self-approval, snowflake, email-gate, git-clone) asserting the correct outcome, **chain ordering**, the per-gate **action** (email→`request_bash_gate`, destructive→`request_destructive_gate` — D-A), and the **env-strip** + **guard-absence direction** — not just "bash/edit reached" (C6). Entrypoints: OpenCode `NanoclawGuard()['tool.execute.before']`; Codex `runHookForCodex`/`runPreToolUseChain`; Claude PreToolUse chain. **Guard-absence assertion (M4/A10 + cycle-4 M1):** assert each adapter's now-**uniform fail-closed** direction (after the D-E flips) — covering **both** Codex container-side cores (destructive AND file-protection) plus the malformed/throwing-core paths, not just the destructive core; the prior "blanket deny" assertion would have failed against today's fail-open Codex (two paths). **The denylist is NOT a dispatch-coverage case (D-D/C3-2):** there is no runtime OpenCode denylist to drive. On Claude/Codex the denylist is enforced by the SDK `disallowedTools` config arg (claude.ts:1290) **and** the chain-dispatched `preToolUseHook` (claude.ts:236-244; on Codex it is the first chain hook at runner.ts:222) — so it IS chain-dispatched on Claude/Codex (A-Finding-5 precision), but the **OpenCode** chain dispatches no denylist guard. Denylist parity is verified separately by the recurring OpenCode tool-enumeration test (D-D) + a config-time assertion that Claude passes `SDK_DISALLOWED_TOOLS` and Codex re-exports the same symbol (runner.ts:358) — wiring, not an OpenCode dispatch case.

*Options:* (lighter) co-located per-adapter table-driven dispatch tests **[chosen]**; (heavier) vendored shared dispatch module + vendored `.test.ts` — rejected (cross-repo import + non-standard test vendoring). **Confidence: High.**

### D-H · shared-core layout + vendor (C11 + S4)
**Chosen:** extend `block-destructive-core.ts` for the two small additions (`evaluateSelfApproval`, `evaluateSnowflakeConnector`) — no `VENDORED_FILES` change; add **one new `email-gate-core.ts`** → add to `VENDORED_FILES` (vendor-guards.mjs:33) + `--check`. **Module split for the OpenCode email path (A-Finding-3):** the email *verdict* lives in the new `email-gate-core.ts` (`evaluateEmailSend`), while the email *gate round-trip* (`runEmailGate`→`pollDeliveredTable`) lives in the already-vendored `block-destructive-core.ts` — so OpenCode's email path imports from **both** vendored modules (`email-gate-core.ts` is the only NEW vendor entry). **`SDK_DISALLOWED_TOOLS` is NOT added here** — per D-D it stays single-source in nanoclaw `claude.ts:114-124` and is never vendored. **S4/A7/A11 invariant (state explicitly):** in one container, Claude/Codex dynamic-import the *vendored* `workflow-agents` core while OpenCode imports the *SoT* `workflow` core (relative) — `vendor-guards --check` (byte-equality per `VENDORED_FILES`) is what prevents divergence. **Required-CI-gate (cycle-4 C4 + B-MED):** `--check` runs as a **required CI gate in the bootstrap repo** (`.github/workflows`), not only as a pre-commit hook + build-checklist step — so a skipped local pre-commit cannot let a stale vendored copy merge. **Differential-cores assertion (B-LOW1):** beyond byte-equal `--check`, the conformance suite imports BOTH the SoT `workflow` core and the vendored `workflow-agents` core and asserts they return **identical verdicts** over the fixed corpus — supplemental *behavioral* coverage that fires even if `--check` were somehow skipped (it does NOT replace `--check`: corpus-equivalence can't prove parity on an un-covered command pattern — C4 — so byte-equality stays the primary gate, the differential is defense-in-depth). **Packaging tradeoff (B-MED, acknowledged):** vendoring is the industry's discouraged-by-default cross-repo sharing mechanism; the all-three-adapters-share-one-policy guarantee for a single container rests on the `--check` CI gate + the differential test doing the work a published package or git submodule would otherwise do. This is accepted under the HARD two-repo / no-shared-registry constraint (C2/C5); **growth in `VENDORED_FILES` beyond a handful of core files is the explicit trigger to revisit packaging** (published `@nanoclaw/guard-core` or submodule).
