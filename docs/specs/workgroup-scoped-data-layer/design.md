# Design: Workgroup-Scoped Data Layer for Sibling Agents

> Generated by `/team-design` — 2026-05-18
> Revised — 2026-05-18 (cycle-1 + cycle-2 review feedback)
> Saved to: `docs/specs/workgroup-scoped-data-layer/design.md`

## Brief Reference

Formalize **workgroup** as a first-class layer above `agent_groups`. A workgroup pools chat archive, mnemon recall, and OneCLI secret declarations across member agent_groups (parent + codex twin and future siblings like `<x>-research`). Sibling agent_groups remain separate rows for routing/identity; workgroup is the layer above. See `brief.md` for full requirements and constraints.

## Options

### Option A: Workgroups table + workgroup_id column on agent_groups *(recommended)*

**Approach:** Add `workgroup_id TEXT` column to `agent_groups`. Add new `workgroups(id TEXT PRIMARY KEY, display_name TEXT, onecli_secrets TEXT JSON, created_at TEXT, updated_at TEXT)` table for canonical workgroup metadata. `container.json.workgroup_id` declares membership per group (operator-facing SoT). DB column carries the derived view used by projection queries.

**Pros:**
- Workgroup is a canonical DB entity — single query target for workgroup-level metadata
- OneCLI secret inheritance has a clean home (no scattered config across N member container.json files)
- Future workgroup-level fields (display_name, owner, archived_at, etc.) plug in via single ALTER TABLE
- Migration is one schema_version bump bundling schema + backfill (matches `031-inbox-board-foundations.ts` pattern)
- Projection query is a single subquery: `WHERE agent_group_id IN (SELECT id FROM agent_groups WHERE workgroup_id = ?)`

**Cons:**
- Two-table schema delta instead of one column
- container.json is the operator-facing SoT but the DB column is what projection queries hit — needs a reconciler when container.json changes (handled at create_agent and spawn paths; matches existing `agentGroupId` propagation pattern)

**Pattern alignment:** Matches CLAUDE.md § "Central DB" — shared metadata lives in `v2.db`, per-agent projection is the read interface. Mirrors how `messaging_groups` carries shared metadata that `messaging_group_agents` references via FK-like indirection.

**Confidence:** High — all components are already in the codebase, change is additive, no external dependencies.

**Assumptions:**
- `agent_groups.folder` (UNIQUE column) is sufficient to derive workgroup_id at migration time for current sibling pairs without operator action
- Operators are willing to declare `workgroup_id` in container.json for new groups going forward (matches the existing `agentGroupId` declaration pattern)

---

### Option B: Tag-only workgroup (no workgroups table)

**Approach:** Add `workgroup_id TEXT` column to `agent_groups` only. Workgroup-level OneCLI secrets live as a special key in EVERY member's container.json (e.g. `workgroupOnecliSecrets`). Workgroup is implicit — any distinct workgroup_id value defines one.

**Pros:**
- Schema is one new column; no new table
- No DB-to-FS reconciliation needed — container.json is sole SoT for both membership and secrets
- Smaller migration footprint

**Cons:**
- Workgroup-level secrets duplicated across N member container.json files; drift is operator's problem (the same kind of bug we just fixed with PR #105 for `MNEMON_STORE_<folder>` casing)
- No canonical "workgroup row" — can't enumerate workgroups except via `GROUP BY workgroup_id` on agent_groups; can't add workgroup-level metadata without rebuilding the pattern
- Future workgroup-level fields (display_name, owner, etc.) compound the duplication
- Doesn't match Central DB pattern for shared metadata

**Pattern alignment:** Partial — fits container.json-per-group convention but not Central DB shared-metadata convention. Pushes future complexity onto operators.

**Confidence:** Medium — works for the immediate need, accumulates cost as workgroup-level fields proliferate.

**Assumptions:**
- Workgroup-level metadata stays minimal forever (just OneCLI secrets)
- Operators tolerate manual cross-file sync

---

### Option C: Filesystem-driven workgroup config

**Approach:** New `groups/<workgroup>/workgroup.json` file declares workgroup metadata (display_name, onecli_secrets, members). Members' container.json declares `workgroup_id`. Optional DB column on agent_groups for fast lookup, populated by group-init / explicit sync step.

**Pros:**
- Workgroup config lives in its own file at a stable filesystem path
- Matches the existing `groups/<folder>/` convention for per-agent config
- No new DB table required if scope-resolver and projection both read filesystem

**Cons:**
- Where does `workgroup.json` live? At one designated member's folder (which?), or a new `workgroups/<id>/` top-level dir? Either way adds a new filesystem topology
- Two SoTs to keep in sync (workgroup.json + agent_groups DB column), unless we accept slower filesystem walks at spawn time
- Doesn't compose with the channel/provider skill installer pattern — those skills drop files into `groups/<folder>/`, not into a workgroup-level dir
- Filesystem walks at spawn time are slower than a JOIN; matters at high-frequency spawn paths

**Pattern alignment:** Partial — matches per-group filesystem pattern but creates a new layer not present elsewhere.

**Confidence:** Medium — workable but introduces a new abstraction layer; DB option is simpler and more consistent.

**Assumptions:**
- Operators are willing to maintain a workgroup-level filesystem topology
- Filesystem walks acceptable at spawn time (currently per-agent projections execute synchronously on every spawn)

## Recommendation

**Selected: Option A** — workgroups table + workgroup_id column on agent_groups.

**Justification:** Three observations make this dominant:

1. **Workgroup is shared metadata** — that's exactly what Central DB is for (CLAUDE.md § "Central DB"). Container.json is for per-group config; workgroup-level config belongs higher in the topology, in the DB.
2. **OneCLI secret inheritance needs a home.** Option B duplicates secrets across N container.json files — re-creating the exact class of bug we just fixed with PR #105 (drift between hand-edited config and runtime). Option C scatters secrets into filesystem with slower lookup. A `workgroups` table is the right shape.
3. **Future-proofing is cheap with Option A.** New workgroup-level fields are one ALTER TABLE. Options B and C compound their respective tax with each new field.

### Sub-decisions (folded into Option A, revised after cycle-1 review)

#### Identifier semantics (M2 + cycle-2 S1)

`workgroup_id` and `workgroups.id` are both the **folder slug** (e.g., `"axie-dev"`, `"madison-reed"`).

**Asymmetry note** (cycle-2 S1): on Dave's install, parent agent_groups carry opaque `ag-<ts>-<rand>` ids while codex twin agent_groups carry slug-equal-id (e.g., `agent_groups.id = "madison-reed-codex"`). So `workgroup_id = folder_slug` is:
- For parents: `workgroup_id (= folder) ≠ agent_groups.id`
- For codex twins: `workgroup_id (= folder) = agent_groups.id` (incidentally — clone-as-codex stamps id as folder slug)

Rationale for picking slug: operator-facing handle, matches `container.json` declaration convention, `agent_groups.folder UNIQUE` makes the namespace clean. Standalone groups end up with `workgroup_id = own folder name`.

**CHECK constraint** (cycle-2 S1): `workgroups.id` must match the slug pattern (`^[a-z][a-z0-9-]*$`, not matching `^ag-`) to prevent future opaque-id contamination.

**Trade-off acknowledgment** (cycle-2 S8): slug-as-PK has known mainstream drift (GitHub 2024 moved client_id to opaque). For Dave's install (10 stable pairs, no rename activity), slug-as-PK is acceptable. Future-proofing path: if rename activity emerges, a follow-on migration adds an opaque PK with slug as UNIQUE column.

#### Declaration model & membership SoT (M1)

- **Operator-facing SoT:** `container.json.workgroup_id` is what the operator edits.
- **Runtime canonical:** `agent_groups.workgroup_id` (DB column) is what projection and scope-resolver query.
- **Reconciliation:** host re-reads container.json on every spawn, upserts into `workgroups` + updates `agent_groups.workgroup_id` in a single transaction (see Reconciliation pseudocode below).
- **Scope-resolver `'workgroup'` mode**: reads from `agent_groups.workgroup_id` in the central DB, NOT from filesystem. Replaces the existing filesystem-walk pattern (`scope-resolver.ts:40` `getAllMemoryEnabledGroupIds`) for this mode only — other modes (`'all-groups'`, folder list) retain their filesystem behavior for backward compat. Same 60s cache TTL.

#### Schema (M3, M7, cycle-2 M2)

```sql
CREATE TABLE workgroups (
  id              TEXT PRIMARY KEY CHECK (id GLOB '[a-z]*' AND id NOT LIKE 'ag-%'),
  display_name    TEXT,
  onecli_secrets  TEXT NOT NULL DEFAULT '[]',
  mnemon_store_id TEXT,                          -- canonical store id; backfilled to parent's agent_groups.id (cycle-2 M1)
  created_at      TEXT NOT NULL,
  updated_at      TEXT
);
```

**NOT NULL enforcement via table rebuild** (cycle-2 M2): SQLite `ALTER TABLE ADD COLUMN NOT NULL REFERENCES` is rejected on a populated table. Migration 036 uses the standard table-rebuild dance to install the constraint at the schema layer:

```sql
-- 1. Create new agent_groups with the NOT NULL constraint
CREATE TABLE agent_groups_new (
  -- ...all existing columns from migration 001...
  workgroup_id TEXT NOT NULL REFERENCES workgroups(id)
);

-- 2. Copy data with the backfilled workgroup_id
INSERT INTO agent_groups_new SELECT ..., <backfilled_workgroup_id> FROM agent_groups;

-- 3. Drop old, rename new
DROP TABLE agent_groups;
ALTER TABLE agent_groups_new RENAME TO agent_groups;

-- 4. Re-create the index on workgroup_id
CREATE INDEX idx_agent_groups_workgroup_id ON agent_groups(workgroup_id);
```

All inside one transaction. Ordering: CREATE workgroups → INSERT workgroups rows (with mnemon_store_id backfill per cycle-2 M1) → rebuild agent_groups → validate W1+W2 → bump schema_version.

#### Workgroup-runtime invariants (M9)

- **W1.** Every `agent_groups` row has a non-null `workgroup_id` after migration. Backfill validates before `schema_version` bump.
- **W2.** Every `agent_groups.workgroup_id` references an existing `workgroups.id`. FK enforces.
- **W3.** Projection build fails closed if the spawning agent has an invalid workgroup_id (NULL post-init, or FK violation due to deleted workgroup row). `buildArchiveProjection` throws — caller (`src/container-runner.ts:1787` area) catches and aborts spawn rather than producing an empty or self-only projection. Logged loudly.

#### Backfill heuristic (D6, refined)

- Iterate `agent_groups` rows ordered by `created_at`.
- For each row with `folder` ending in `-codex`:
  - Strip `-codex` to get parent slug.
  - If a row exists with `folder = <parent>`, BOTH go into workgroup `<parent>` (sibling pair).
  - If no parent row exists, this codex row is standalone → workgroup = own folder.
- All non-`-codex` rows that weren't paired get workgroup = own folder.

**Backfill report** (S7): the migration logs a structured summary — `paired: [(child, parent), ...]`, `standalone: [...]`, `suffix_strip_unmatched: [...]` — to `logs/migration-036.log` so the operator can verify pairings before further actions.

#### Per-table pooling strategy (M5)

|---|---|---|---|
| `messages_archive` | **YES** (via `buildArchiveProjection`) | **DROP** at `thread-search.ts:225, 359-366, 515-531` | siblings share chat history (R2) |
| `backlog_items` | NO (stay agent-scoped) | KEEP at `backlog.ts:273, 281, 326, 342` | each agent's todo list is its own |

`buildCentralProjection` already accepts a per-table filter column map (`per-agent-projections.ts:145-150`) — leave existing logic for the four central tables; only `buildArchiveProjection` gains workgroup widening.

#### Pooled archive dedup (M4 + cycle-2 M3+M4)

`router.ts:793, 916, 932` writes one archive row per agent that received an inbound user message (via `messageIdForAgent`). Pooled workgroup projection would surface those as N copies of the same user message.

Dedup is projection-only. `buildArchiveProjection`'s source SELECT becomes (full column list with explicit aggregators, deterministic surviving id):

```sql
SELECT MIN(id) AS id,
       MIN(agent_group_id) AS agent_group_id,
       messaging_group_id,
       MAX(channel_type) AS channel_type,
       MAX(channel_name) AS channel_name,
       MAX(platform_id) AS platform_id,
       thread_id,
       role,
       sender_id,
       MAX(sender_name) AS sender_name,
       text,
       sent_at,
       MIN(created_at) AS created_at
  FROM messages_archive
 WHERE agent_group_id IN (SELECT id FROM agent_groups WHERE workgroup_id = ?)
 GROUP BY messaging_group_id, thread_id, role, sender_id, sent_at, text
```

**Critical: `sender_id` is in the GROUP BY** (cycle-2 M4). For user rows, `sender_id` = originating user (same across both sibling archive copies) → dedup still works. For assistant rows, `sender_id` = `agent_group_id` (per `delivery.ts:697`) → differs per sibling → guaranteed distinct, never collapses regardless of text/sent_at coincidence.

`MIN(id)` for the surviving row's id is deterministic across spawns (fixes FTS rowid non-determinism per cycle-2 S3). Test: pooled projection of two-sibling pair has exactly one user-message row per sent message; both siblings' assistant responses preserved as distinct rows.

#### Mnemon store routing (M6 + cycle-2 M1 CRITICAL)

Single store per workgroup. `workgroups.mnemon_store_id` is the canonical store identifier. All workgroup members read/write the same store via `MNEMON_STORE=<workgroups.mnemon_store_id>` at spawn.

**CRITICAL: backfill mnemon_store_id to preserve existing recall history** (cycle-2 M1). Existing mnemon stores on Dave's install are keyed on `agent_groups.id` (verified: illie's store is at `~/.mnemon/data/ag-1776377699463-2axxhg/mnemon.db` with 43MB of accumulated facts). The backfill MUST preserve these paths:

For each backfilled workgroup, the migration sets `mnemon_store_id` to the **parent member's existing `agent_groups.id`**:

```typescript
// Migration 036 backfill, after agent_groups population:
for (const workgroup of backfilledWorkgroups) {
  // The "parent" row is the one whose agent_groups.folder = workgroups.id (slug)
  const parentRow = db.prepare(
    'SELECT id FROM agent_groups WHERE folder = ? LIMIT 1'
  ).get(workgroup.id);
  if (!parentRow) {
    throw new Error(`Migration 036: workgroup ${workgroup.id} has no parent agent_groups row`);
  }
  db.prepare('UPDATE workgroups SET mnemon_store_id = ? WHERE id = ?')
    .run(parentRow.id, workgroup.id);
}
```

Net effect: workgroup `illysium` → `mnemon_store_id = 'ag-1776377699463-2axxhg'` (illie's existing store path). Container's `MNEMON_STORE=ag-1776377699463-2axxhg` matches today's value. Zero data loss; 43MB recall history preserved.

**Read path:**
- `container-runner.ts:1775` reads `workgroups.mnemon_store_id` for the spawning agent's workgroup; sets `MNEMON_STORE=<that_id>`.
- `MNEMON_STORE_<folder>` env override (PR #105's case-insensitive lookup) STAYS in place per C6 — when set, overrides the workgroup-derived value (transition-state redundancy; cleanup is a future PR).

#### OneCLI secret merge semantics (D8, refined)

Workgroup baseline ∪ per-group additive. Computed in `container-runner.ts` (spawn path, around line 1787) before `applyOnecliSecrets`. Per-group can extend, cannot subtract.

**Validation at write time, not spawn time (S6):** when an operator (or migration) writes to `workgroups.onecli_secrets`, the host eagerly resolves names → UUIDs via `onecli-secrets.ts` `resolveSecretUuids`. If any name is unresolvable, the write is rejected with a loud error. This prevents one bad name from blast-radiusing every member's spawn. Resolved UUIDs are stored in `workgroups.onecli_secrets` as JSON `[{name, uuid}]` for fast spawn-time lookup.

**Duplicate-secret report (S10):** the migration enumerates per-workgroup intersection of member-level `container.json.onecliSecrets` entries. Logs candidates for operator-driven consolidation (`logs/migration-036-secrets.log`). Out of scope: any automated rewrite of member container.json files.

#### Reconciliation pseudocode (S3 + cycle-2 S2)

On every spawn (`src/container-runner.ts:1644+`), compress the read-decide-write into a single atomic UPDATE to avoid TOCTOU (cycle-2 S2):

```typescript
const cc = readContainerConfig(folder);
const declared = cc.workgroup_id ?? agentGroup.folder;  // operator intent

db.transaction(() => {
  // Insert workgroup row idempotently. ON CONFLICT DO NOTHING signals intent vs OR IGNORE.
  db.prepare(`INSERT INTO workgroups (id, display_name, onecli_secrets, mnemon_store_id, created_at)
              VALUES (?, ?, '[]', ?, datetime('now'))
              ON CONFLICT(id) DO NOTHING`).run(declared, declared, agentGroup.id);

  // Atomic check-and-set: only update if value actually changes
  db.prepare(`UPDATE agent_groups SET workgroup_id = ?
              WHERE id = ? AND (workgroup_id IS NULL OR workgroup_id != ?)`)
    .run(declared, agentGroup.id, declared);
})();
```

Race-safe: concurrent spawn + create_agent both target the same row; both statements are idempotent and atomic-within-statement. SQLite serializes the transactions.

Note: a NEW workgroup created by spawn-time reconciler gets `mnemon_store_id = agentGroup.id` (the spawning agent's own id). For pre-existing workgroups (already in DB), the `ON CONFLICT DO NOTHING` preserves the migrated `mnemon_store_id`.

#### Migration shape (cycle-2 M2 + M5)

Single migration `036-workgroup-id.ts`. Single SQLite transaction wraps schema + backfill + validation. Container.json writes happen post-transaction with explicit recovery path (cycle-2 S7).

```typescript
db.transaction(() => {
  // 1. Create workgroups table (no agent_groups changes yet — table rebuild comes after backfill)
  db.exec(`
    CREATE TABLE IF NOT EXISTS workgroups (
      id              TEXT PRIMARY KEY CHECK (id GLOB '[a-z]*' AND id NOT LIKE 'ag-%'),
      display_name    TEXT,
      onecli_secrets  TEXT NOT NULL DEFAULT '[]',
      mnemon_store_id TEXT,
      created_at      TEXT NOT NULL,
      updated_at      TEXT
    )
  `);

  // 2. Read existing agent_groups + classify
  const rows = db.prepare('SELECT id, folder FROM agent_groups ORDER BY created_at').all();
  const folderSet = new Set(rows.map(r => r.folder));
  const pairings: {child: string, parent: string}[] = [];
  const standalone: string[] = [];
  const suffix_strip_unmatched: string[] = [];
  const workgroupForRow = new Map<string, string>();  // agent_groups.id → workgroup_id

  // Cycle-2 M5 fix: correctly classify orphan -codex rows as unmatched, not standalone
  for (const row of rows) {
    let wg: string;
    if (row.folder.endsWith('-codex')) {
      const parent = row.folder.slice(0, -'-codex'.length);
      if (folderSet.has(parent)) {
        wg = parent;
        pairings.push({ child: row.folder, parent });
      } else {
        wg = row.folder;
        suffix_strip_unmatched.push(row.folder);  // orphan twin — flag for operator
      }
    } else {
      wg = row.folder;
      standalone.push(row.folder);
    }
    workgroupForRow.set(row.id, wg);
  }

  // 3. Insert workgroups rows (mnemon_store_id backfill comes in step 4)
  const insertWg = db.prepare(`
    INSERT INTO workgroups (id, display_name, onecli_secrets, created_at)
    VALUES (?, ?, '[]', datetime('now'))
    ON CONFLICT(id) DO NOTHING
  `);
  for (const wg of new Set(workgroupForRow.values())) {
    insertWg.run(wg, wg);
  }

  // 4. Backfill mnemon_store_id to PARENT'S existing agent_groups.id (cycle-2 M1 — CRITICAL)
  // For each workgroup, the "parent" row is the one whose folder = workgroups.id (the slug).
  const setStoreId = db.prepare('UPDATE workgroups SET mnemon_store_id = ? WHERE id = ?');
  for (const wg of new Set(workgroupForRow.values())) {
    const parentRow = db.prepare('SELECT id FROM agent_groups WHERE folder = ? LIMIT 1').get(wg);
    if (!parentRow) {
      throw new Error(`Migration 036: workgroup ${wg} has no parent agent_groups row with folder=${wg}`);
    }
    setStoreId.run(parentRow.id, wg);
  }

  // 5. Table rebuild for agent_groups with NOT NULL workgroup_id (cycle-2 M2)
  // SQLite cannot ADD COLUMN NOT NULL REFERENCES — use the standard rebuild dance.
  db.exec(`
    CREATE TABLE agent_groups_new (
      -- all existing columns from migration 001, copied verbatim
      <preserve_existing_columns>,
      workgroup_id TEXT NOT NULL REFERENCES workgroups(id)
    );
  `);

  const insertAgNew = db.prepare(`
    INSERT INTO agent_groups_new (<all_existing_cols>, workgroup_id)
    SELECT <all_existing_cols>, ? FROM agent_groups WHERE id = ?
  `);
  for (const [agId, wgId] of workgroupForRow) {
    insertAgNew.run(wgId, agId);
  }

  db.exec(`
    DROP TABLE agent_groups;
    ALTER TABLE agent_groups_new RENAME TO agent_groups;
    CREATE INDEX idx_agent_groups_workgroup_id ON agent_groups(workgroup_id);
  `);

  // 6. Validation (W1, W2)
  const orphan = db.prepare(`
    SELECT id FROM agent_groups
    WHERE workgroup_id IS NULL OR workgroup_id NOT IN (SELECT id FROM workgroups)
  `).get();
  if (orphan) throw new Error(`Migration 036 validation failed: orphan workgroup_id on ${orphan.id}`);

  // Store report data on closure for post-transaction file writes
  (this as any).report = { pairings, standalone, suffix_strip_unmatched };
})();

// 7. Post-transaction file writes (cycle-2 S6, S7)
try {
  // Backfill report (S7 + cycle-2 S6)
  fs.mkdirSync('logs', { recursive: true });
  fs.writeFileSync(
    'logs/migration-036.log',
    JSON.stringify(report, null, 2) + '\n'
  );

  // Duplicate-secrets report (S10 + cycle-2 S6)
  // ... compute per-workgroup intersection of member onecliSecrets ...
  fs.writeFileSync('logs/migration-036-secrets.log', secretsReport);

  // Container.json recall_scope writes for auto-paired groups (M8)
  for (const { child, parent } of report.pairings) {
    for (const folder of [child, parent]) {
      const cfg = readContainerConfig(folder);
      cfg.memory = { ...(cfg.memory ?? { enabled: true }), recall_scope: 'workgroup' };
      writeContainerConfig(folder, cfg);
    }
  }
} catch (fsErr) {
  // Cycle-2 S7: SQL succeeded but FS writes failed. Log loudly; provide recovery script path.
  log.error('Migration 036 SQL committed but post-transaction writes failed', {
    err: fsErr,
    recovery: 'Run `pnpm exec tsx scripts/migration-036-fs-writes.ts` to retry idempotently',
  });
  throw fsErr;
}
```

The recovery script `scripts/migration-036-fs-writes.ts` (cycle-2 S7) re-reads `agent_groups.workgroup_id`, recomputes pairings, and writes container.json + logs idempotently — no DB writes, just FS. Safe to run after the SQL transaction has committed but FS writes failed.
