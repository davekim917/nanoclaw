# Outcome-first work-item reporting

Authorized outcome: useful autonomous work continues quietly. Developers receive one concise contextual report when each original human work item finishes, can request detail or steer, and still receive material incidents, genuinely blocking product/trust/authority decisions and required approvals. No global wake budget, model change, new evaluator, periodic public digest or widened authority.

## Implementation contract

- `container.json` has an optional `outcomeReporting` override and `outcomeReportingExternalChannels`. Absent means the fleet default (enabled); literal false is the rollback. The spawn-only `NANOCLAW_OUTCOME_REPORTING=1` capability activates shared runner/MCP behavior, while preserved old containers retain their legacy path. Claude, Codex and OpenCode receive the same generated contract. The optional value stays absent during unrelated config writeback so the default remains reversible.
- Existing send_message accepts purpose: progress/outcome/reply/urgent/decision/handoff. Under opt-in, channel sends require purpose; progress writes work_log instead of chat. Internal agent destinations keep their existing routing and permissions. Human requested replies can be detailed; real urgent/authority paths and existing questions/cards/approvals remain available. Existing task mute/budgets are not widened; muted watcher reports retain the outbox/card route.
- Final/interim model narration is internal. It never increments sent or satisfies reply-debt. The existing once-per-batch reply nudge directs the agent to send_message, not an internalized message block. An explicit internal 'no reply' remains possible for acknowledgments that warrant silence. Suppressed task and interim message blocks are durable work_log records. A task that attempts an explicit message receives one tool-directed recovery nudge only when its budget permits and no notification was already queued. Plain background narration never causes a recovery turn. Missing replies are archived as undelivered rather than falsely completed.
- Routine outcome payload requires a short product result, verified result, and optional HTTPS evidence/material remaining/needs-you fields. Target about 60 words; oversized output is rejected, never silently truncated. Existing normalized GitHub PR/issue and Slack request URLs remain valid. Other work uses an inbound message id supplied by the harness; the host resolves it back to this session's trusted row and derives an opaque key from the protected platform origin when available, so sibling copies of one request dedupe without user-created keys. Semantic completion and choosing the original request among several supplied ids remain agent judgments.
- Host destination authorization remains first. One atomic unique central receipt claim then serializes actual workgroup + canonical item across siblings/sessions. The tool queues, reads existing inbound delivery acknowledgment, and distinguishes confirmed receipt, failure and unconfirmed. Existing delivered tables are PER-SESSION inbound tables: src/db/schema.ts begins INBOUND_SCHEMA at175; src/mailbox/sqlite/index.ts opens/migrates the session inboundPath. They cannot provide work-item dedupe.
- A successful adapter return is acknowledged even if it supplies no platform ID. A thrown send with unknown platform acceptance is held, never blindly re-posted. The operator reconcile tool requires current updated_at plus an evidence reason; it can confirm existing delivery, permit the original queued row after verified non-delivery, or correct a confirmed mistaken identity. Operator must drain/reconcile queued copies before rekeying. Receipt history is retained; no normal caller revision escape hatch exists. Material later corrections use existing edits or urgent updates.
- Typed routine outcomes bypass daily task/turn/key auto-anchors. Ordinary original human threads remain; a scheduled outcome tied to an original Slack request can use that exact thread. Unrelated completed work gets independent reports, not one giant daily thread.
- A deployment can reserve a physical channel for an existing terminal reporter through outcomeReportingExternalChannels. Native typed outcomes to that channel are refused, while human replies, approvals and urgent corrections retain their existing routes. The external reporter and its receipts are outside this source contribution; no cross-route or universal exactly-once guarantee is made.

## Producer reconciliation and activation

Install-local producer patches belong in private deployment records. Reconcile role and recurring-task output clauses before enabling the flag; preserve all product/authority decisions, recipient-requested private summaries, release holds, QA publication boundaries and internal handoffs. Do not include install identifiers or history in a source contribution.

Before activation, run `pnpm exec tsx scripts/outcome-reporting-status.ts` and pin any intentional legacy group to false. Coordinate guarded host activation because runner source is a boot snapshot; reconcile existing reporting queues and keep unrelated model/provider fields unchanged. Old containers retain untyped legacy status and reply behavior; fresh containers mark internal narration and deterministic lifecycle state with the versioned capability. A typed working row is deleted by a delivered reply/outcome and changed to stopped on a no-result turn or kill. The host recovers its platform id after restart from the original mailbox receipt; once a public response supersedes the activity line, an additive nullable marker on that same receipt prevents every recovery path from reviving it as live without rewriting the platform delivery identity. Observe fresh natural behavior separately from saved configuration.

## Verification and review

Tests cover default-on/explicit-false groups, three-provider contract parity, old/new mixed-version rows, internal records/reply debt, bounded tool nudge, requested detail, legacy and opaque identity, cross-sibling origin dedupe, forged request ids, optional evidence, truthful host acknowledgment, lifecycle recovery, questions, authorized/denied routes, unknown sends, later correction, independent task roots, external-lane exclusion and reconciliation preconditions. Use fake transports and isolated DBs only. Run affected runner/host tests, host+scripts and runner typechecks, required lint, formatting and upstream ratchet.

Independent cross-family plan and implementation reviews must check reply preservation, authorization before receipt claims, canonical identity, delivery acknowledgment, recovery and legacy compatibility. Deployment procedures and publication boundaries require separate verification. Do not hold asynchronous authorization or network work inside SQLite transactions.
