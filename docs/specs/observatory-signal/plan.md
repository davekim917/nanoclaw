# Observatory 2.0 — Signal

Status: implementation authorized by the user's active build-and-end-to-end-test goal. Signal is the selected design; the other concepts are rejected. Worktree: `/tmp/observatory-signal-build`, branch `feat/observatory-signal`.

## Outcome
Two authorized reviewers can understand autonomous work across workgroups, projects, agents and threads; see what changed; understand and own human decisions; inspect source evidence; and act without guessing what an approval means. The deliverable is a working real-data application, not another static concept. No purple or gradients. All delegated work uses gpt-6-astra at medium; this explicit user pin overrides the workflow's cross-family reviewer default. No automatic merges, deployments of other products, or real approval decisions during testing.

## Current evidence
- `dashboard/src/main.tsx` mounts only ThreadConsole. Its existing queue, transcript, composer, schedule, snooze, assignment and guarded close are useful operational primitives.
- `dashboard/src/lib/api.ts` exposes workgroups, groups, threads, scene, release-state, claims and issue briefs. `src/dashboard/index.ts` registers authenticated routes under `/dashboard/api`; `/observatory/` serves the SPA.
- `src/dashboard/api/threads.ts` is scope-filtered and thread-keyed, preventing duplicate multi-agent conversations. Needs-you reasons distinguish parked notes, questions and task input. Attention is not an executable approval.
- `src/dashboard/api/observatory.ts` returns release-board data but its scene is whole-workgroup visibility. New endpoints must explicitly enforce their data boundary rather than assume scene grants imply per-agent access.
- The live the shared workgroup release-state currently contains human decisions with question, why, next action and owner hints that the PR-only attention producer omits. The source also contains old/inconsistent claims. Preserve provenance and freshness; never turn source prose into a verified runtime fact.
- There is no authoritative project table. Group/channel/project associations need explicit mappings; unmapped work stays visible.
- Existing pending approvals and their action handlers enforce separate approval semantics. Never resolve a privileged approval through ordinary chat or call the host-operator bypass from a web endpoint.
- DB migration to async driver is in progress. New state uses getDb and atomic single-statement compare-and-set. No new raw DB imports or driver transactions.

## Design and behavior
1. Signal is the application shell and default overview: compact rail, near-black canvas #101112, #191b1d surfaces, #eef0f2 text, #adb4bb secondary, ivory action #e8ece4, amber attention and mint only evidenced verified state. Embedded/local Geist and Geist Mono. Desktop overview aligns concise project work with a contextual decision pane. Mobile places decision before project rows; all screens usable at 390px without horizontal page overflow.
2. Navigation covers Overview, Projects, Decisions, Agents, Threads and Schedule. Preserve existing thread actions and scheduling semantics; thread deep links identify the exact thread. Real workspace selector, search and browser navigation must work. All-workgroups view must not silently omit a workgroup.
3. Project visibility uses explicit source-backed repository/project mapping with goal, owner, associated channels or release items and dependencies when declared. Do not infer project identity from arbitrary chat title text. Unmapped items/threads are a first-class bucket. Show counts, next steps, source timestamps, missing-data and stale-source indicators. Unknown dependency is distinct from checked-independent.
4. Decision inbox combines source-declared human release items (all kinds), thread questions/input and actual pending approval metadata. Each retains source kind/id/version, question, why, next step/recommendation where actually supplied, source owner hint, evidence links/transcript and consequences if supplied. Missing context is stated and can be inspected; no invented recommendation or scope. Correlate only by exact source/thread references, not fuzzy title similarity.
5. Shared review ownership is persisted per source decision/version with real authenticated user IDs, claim/release/reviewed/resolved state and decision note. CAS revision prevents Two authorized reviewers overwriting each other. A change in source version reopens review and preserves previous decision history. Source disappearance is not proof of completion. Recorded decisions are distinguished from successfully delivered instructions and completed agent work.
6. Human-authored instruction submission uses existing authenticated thread/steer paths with explicit recipient and idempotency. A recorded note alone never claims an agent received it. Existing privileged approval cards retain their genuine authority and original destination; expose safe metadata and an exact source link when web resolution cannot preserve those semantics. Do not implement a generic Approve button for an untyped needs-you row.
7. Real agent view shows persona, provider, active vs merely awake, recent work, linked threads, claims and next scheduled work. Activity presents actual events/timestamps, not fabricated summaries or completion percentages.
8. Refresh on SSE and revalidate on reconnect/focus. Filesystem release sources require a bounded refresh cadence or actual change event; do not assume session SSE covers file updates. Surface disconnected, loading, failed, empty, stale and partially available states. Bound concurrency, payloads and transcript reads; selected evidence only.
9. Auth is enforced server-side on every read and mutation. Project/board workgroup data must require explicit workgroup visibility policy. Agent/thread/approval data is intersected with allowed groups. Human assignment never grants authority. Reject forged source IDs, cross-workgroup linkage, malformed JSON and stale revisions; never expose opaque credential approval payloads.

## Executable acceptance criteria
- `signal defaults to overview and preserves deep links`: mounting authenticated app shows Signal; projects/decisions/agents/threads/schedule and back navigation reach the intended view; exact thread deep link opens that thread.
- `overview uses real source records`: returned source IDs/timestamps and counts match seeded authoritative DB/files, including non-PR human decisions and unmapped work; no scenario/demo records.
- `scope filters every source`: unauthenticated access is 401; restricted users cannot read another group's thread/agent/approval or mutate another workgroup decision; project aggregates cannot leak those records.
- `decision context stays honest`: question/reason/recommendation/evidence/owner/source version are preserved; absent context is explicit; needs-you is not rendered as privileged authorization.
- `shared ownership is atomic`: two users claiming same revision yield exactly one success and one conflict; reload and second browser see owner; only authorized users can update.
- `changed evidence requires renewed review`: submitting against old source version returns conflict; refreshed source remains awaiting review and previous note is retained as history.
- `decision delivery is explicit and idempotent`: selected recipient and exact text reach intended isolated test session once; failure remains visible and retry does not duplicate; no unrelated session receives work.
- `pending approvals preserve authority`: safe metadata only, exact target linking, no host-operator bypass or exposure of credential payload; expired/resolved approval not offered as actionable.
- `projects preserve incomplete coverage`: declared dependencies resolve by exact IDs; undeclared/missing mappings are shown as unknown/unmapped and do not disappear.
- `live updates and failures remain visible`: SSE burst is coalesced, reconnect refreshes missed events, file update appears after bounded cadence; partial failures do not show all-clear.
- `mobile and keyboard complete the same workflow`: browser checks at 390x844 and 1440x900, no page overflow, accessible controls, decision inspection/ownership/reply plus navigation usable.
- `existing operations still work`: current thread detail/composer, guarded close, snooze and schedule tests stay green except intentional visual/route expectations updated to Signal.
- `real-data end-to-end verification`: run built app against current authoritative data in an isolated authenticated preview, inspect actual counts/evidence and desktop/mobile screenshots. Mutating verification uses isolated DB/session fixtures and fake transport, never actual approvals or unsolicited Slack messages. Final completion additionally requires a reachable built experience for the user with activation state reported precisely.

## Reviewed implementation contract (normative)
- Wire types live in `src/dashboard/observatory-v2/types.ts`; the frontend imports these as types only. GET `/dashboard/api/observatory/v2?workgroup=<id|all>` returns SignalOverview. GET `/dashboard/api/observatory/v2/decisions/:id` returns SignalDecisionDetail. POST `.../decisions/:id/review` accepts SignalReviewRequest; POST `.../decisions/:id/dispatch` accepts SignalDispatchRequest. PUT `.../projects/:id` takes workgroup_id, name, description, repositories, channel_keys and expected_version. IDs must be opaque stable encoded source identities, never ambiguous globally reused board IDs.
- Workgroup-owned release-board/project data is explicitly shared with users holding any allowed sibling in that workgroup, matching the current board visibility contract. Review mutation requires owner/global-admin or admin_of_group with an allowed sibling in the workgroup. Ordinary members are read-only. Project mapping mutation requires owner/global-admin. Thread/agent/approval data additionally intersects exact allowed agent IDs and must never expand because of board visibility. Aggregate counts use only visible records. Scoped-admin authority to mutate a thread-derived review requires authority for that exact originating group. Named approval restrictions still apply even to global board readers.
- New additive `observatory_projects` stores explicit repositories/channel_keys, description (goal), revision and updated_by/at. Mapping editing is an actual owner-facing application form. Bootstrap repository mappings only from exact source metadata (`meta.repo`) or validated GitHub owner/repository URLs; deterministic repository identity is not inferred from prose. Persist this mapping deliberately via the form/API or a documented source-backed initialization step. Do not automatically call channels projects. Release items without exact mappings and unbound threads stay unmapped.
- New additive `observatory_reviews` stores one source key, workgroup_id, source identity, material evidence hash, version, owner, answer, answered-by/at, dispatch key/state/error/recipient and JSON history. CAS updates the entire record including history atomically in one SQL statement. Never require a second event-table write for durability. Fresh source content is read before mutation; the row CAS binds the reviewed hash/version. Filesystem source read defines the observed snapshot; later changes are detected/reopened on the next read, never claimed to be locked through arbitrary external writes.
- Material evidence hash includes source identity, question, context, next action and relevant reference/head/dependency fields, excluding board asOf, refresh timestamps and human review fields. Thread questions are identified by origin session and question sequence where available, not only thread ID. Load exact question detail before answering. Tests must distinguish an unchanged watcher refresh from changed material evidence and successive questions in one thread.
- Claim takes an unowned record for the authenticated user. Release is permitted for its owner or global administrator. Answer is allowed for the owner (or after atomically claiming an unowned record); a different reviewer gets conflict, not silent overwrite. Each accepted action increments revision and atomically appends history. Repeated idempotency key with identical body returns prior success; changed body with same key conflicts. Source hash change exposes state `changed` and requires a fresh answer; retain prior history and do not dispatch the old answer.
- Dispatch is a separate explicit human action after answer, never an automatic effect of saving a review. Reserve stable key and recipient in the review row before calling existing delivery. Retain pending on uncertain result, failed on definite failure; retry reuses the same persisted key and exact answer/recipient, and reconciles delivery idempotency before marking sent. Successful dispatch is not completed work. Release items without an idempotent delivery path stay inspectable with their exact source thread link until that path is implemented safely; this gap prevents full completion of the relevant dispatch criterion.
- Additional acceptance cases: unchanged asOf does not invalidate a review; successive question sequence creates separate decision history; shared project mapping survives a fresh DB connection; member cannot mutate board review; partial scoped admin cannot see other group's transcript/approval; crash after message delivery before status update retries without duplicate; failed CAS leaves no orphan history. Browser source reads are verified against live data; mutation E2E uses isolated state.
- Unanchored board decisions support explicit selection of an existing visible workgroup thread before dispatch. First dispatch accepts optional target_thread_id, validates workgroup, exact thread visibility and existing participant, and reserves the exact session/text/key atomically. Later retries cannot change destination. This avoids remote thread creation and its unrecoverable post-before-record window while enabling contextual operator instructions. No eligible existing conversation is an explicit unavailable state; the operator retains recorded answer and source evidence. Test cross-workgroup destination refusal and retry target immutability.

## Completion refinements
- Active thread coverage is paginated without an arbitrary date cutoff. API returns per-workgroup offset/limit/has_more/next_offset and the UI offers load more, deduplicating exact IDs; refresh resets pages to avoid stale aggregation. Exact decision/thread deep links resolve independently of loaded overview pages. Tests cover off-page detail and loading additional records.
- Every Signal timestamp uses server-provided installation timezone; missing/invalid zone is explicit rather than silently using browser timezone.
- All non-successful delivery attempts after reservation remain pending/uncertain unless the delivery primitive can prove no overlapping send exists. A non-202 response must never unlock a review while another attempt could still deliver; confirmed sent is terminal. Test both original-fails-first and retry-fails-first interleavings.
