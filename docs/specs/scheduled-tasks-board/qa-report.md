## Validator E — Codex adversarial (cross-model): verdict **needs-attention**, 4 findings — ALL VERIFIED REAL against the code
- **E-1 (CRITICAL → MUST-FIX):** `src/host-sweep.ts:310-343, 386` — `countLiveRowsForSeriesFleetWide` counts `WHERE series_id = ?` across EVERY session in EVERY group (bare `series_id`, not the source/target locator). Since the unique key is `(agentGroupId, sessionId, seriesId)` (operator series like `task-morning-briefing` can collide across groups), a crashed move whose source row was lost + an unrelated same-`series_id` series live in another group → `recoverMoveIntents` line 387 purges-without-restore → **permanent series loss**. The F2 "fleet-wide predicate" is too broad. **Fix:** scope the live-count to the {source session, target session} only (the move_intent must carry the target locator; the move's own compensation path already uses the correctly-scoped `liveRowCountFleetWide(dataDir, source, target, seriesId)` at move.ts:549 — the sweep recovery must use the same 2-location scoping, not the bare-series_id `countLiveRowsForSeriesFleetWide`).
- **E-2 (HIGH → MUST-FIX):** `src/dashboard/api/scheduled-move.ts:504-512, 586-596` — `cancelTask(srcDb, seriesId)` discards its touched count (no CAS: doesn't verify it cancelled a live row), then step 4 inserts the target unconditionally; the step-6 one-live-row invariant is `log.error`-only, NOT enforced (`liveCount !== 1` still returns 200). A concurrent cancel/move/run-now on the same series between snapshot-read and cancel → resurrected/duplicated series, success returned. **Fix:** require `cancelTask` to touch exactly 1 row before scheduling the target (else abort, leave a repairable intent); ENFORCE the invariant — on `liveCount !== 1`, return an error + leave the unresolved intent for sweep recovery, do NOT `purgeIntentBody` + return 200.
- **E-3 (MEDIUM → SHOULD-FIX):** `src/dashboard/api/scheduled-read.ts:160-174` — scoped list returns the FULL-FLEET `unreadable` count (`snapshot.counts.unreadable`) and `degraded` flag to out-of-scope callers, leaking operational state across the scope boundary (softer than existence-disclosure but still crosses C7). **Fix:** track unreadable/degraded per-agent_group during assembly and reduce after `rowInScope`.
- **E-4 (MEDIUM → SHOULD-FIX):** `src/dashboard/api/scheduled-move.ts:129-133` — `computeSecretDelta` hashes only `{gains, losses}`; `confirmedDeltaHash` is replayable across different move targets with identical secret deltas — the TOCTOU guard doesn't bind the target/wiring/crossWorkgroup/scriptPresent the operator actually confirmed. **Fix:** hash a canonical preview payload incl. source key + targetAgentGroupId + targetMessagingGroupId + resolved channel + wiringOk + crossWorkgroup + scriptPresent + gains + losses.

### concurrency-reviewer — 0 MUST-FIX, 4 SUGGESTION (+ a key reconciliation)
**Verdict: no must-fix concurrency bugs.** Traced every interleaving against code. Architectural basis: dashboard handlers + the 60s host-sweep share ONE Node event loop; better-sqlite3 is synchronous; every admit→write runs in a SYNCHRONOUS span (zero await between the live-row READ and status WRITE), so handlers serialize and exactly-one-live-row holds. Verified no-await spans: move read(436)→cancel(508); compensation count→restore(546-583); recovery re-check→restore(424-439). Every UPDATE carries `status IN ('pending','paused')` → losing racer touches 0 → clean 409.
- **CONC-S1 (SHOULD-FIX, substantive):** read-your-own-write gap — `assembleSnapshot` single-flight (`scheduled-assembly.ts:608`) is unconditional `if (inFlight) return inFlight`; the generation counter only blocks CACHING a stale snapshot, not RECEIVING the in-flight one. A list caller arriving after a mutation's `invalidateScheduledCache` (gen→6) but during an in-flight assembly started at gen=5 gets PRE-mutation rows → violates the §3a read-your-own-write guarantee the module header claims. Bounded (self-heals at 5s TTL + SSE refetch). Fix: stamp inFlight with its start-gen; if `cache.gen !== inFlightGen` when a new caller arrives, start a fresh assembly.
- CONC-S2 (ADVISORY): recovery-vs-stalled-move 2-row scenario — confirmed UNREACHABLE (scheduleTask has no blocking await; continuation completes in microseconds, long before the 60s sweep). Theoretical only.
- CONC-S3 (SHOULD-FIX): single-flight ignores its `scopes`/`options` args — safe only because the sole prod caller passes {no_filter:true}+identical opts then scope-filters post-hoc. A future 2nd caller-shape would get the wrong snapshot. Fix: assert/document the single-caller invariant, or key single-flight by scope+opts.
- CONC-S4 (SHOULD-FIX, defensive): staged-paused move (`scheduled-move.ts:523-532`) — if `targetSessionIdFor` returns null after a successful scheduleTask, pauseTask + process_after restore are skipped → the row stays PENDING and fires after GUARD_GRACE instead of paused. Unreachable in practice (scheduleTask just created that session) but undefended. Fix: treat null tgtSessId as a failed stage (compensate/assert).
- Explicitly CLEARED: cross-scope cache poisoning, invalidate-ordering (always after write commit), seq-UNIQUE races, double-restore on crash, overlapping sweep ticks, setImmediate event-loop blocking.
