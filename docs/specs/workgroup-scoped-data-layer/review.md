## MUST-FIX Findings (cycle 3)

### [M1] Table-rebuild for `agent_groups` is incompatible with `PRAGMA foreign_keys=ON` inside a transaction

- **Raised by:** Reviewer A (#1 HIGH), Reviewer B (PRIMARY DRIFT — HIGH severity, T1 sqlite.org + Rails CVE Oct 2025)
- **Finding:** Cycle-2 M2 introduced a table-rebuild dance (`CREATE new → INSERT SELECT → DROP → RENAME`) to install `workgroup_id NOT NULL REFERENCES`. SQLite docs (T1) require `PRAGMA foreign_keys=OFF` BEFORE opening the transaction OR `PRAGMA defer_foreign_keys=ON` INSIDE the transaction; otherwise `DROP TABLE agent_groups` triggers cascade behavior on FK-referencing tables (`sessions`, `messaging_group_agents`, `agent_group_members`, `user_roles`, `agent_group_capabilities`). The codebase runs with `foreign_keys=ON` per project default. The cycle-2 design's "single transaction wraps schema + backfill" cannot achieve correct FK handling because `PRAGMA foreign_keys` is a no-op inside an open transaction.
- **Effort to Fix:** Medium — the simpler resolution is to abandon the table-rebuild entirely.
- **Impact if Ignored:** Critical — migration would fail on first run on any populated install, with possible cascade-delete or FK-violation aftermath.
- **Suggested resolution:** **Drop the table-rebuild approach.** Use `ALTER TABLE agent_groups ADD COLUMN workgroup_id TEXT REFERENCES workgroups(id)` (column nullable in schema). Enforce W1 (non-null) at application layer:
  - Migration validation at tail (already present): `if (orphan) throw` covers post-backfill rows
  - Runtime W3 (already present): fail-closed projection when workgroup_id is NULL or FK-violating
  - Future call sites that INSERT agent_groups rows are bounded to two: `create_agent` path and migration backfills; both can be coded to require workgroup_id

  Trade-off: future code path inserting agent_groups without workgroup_id won't be caught at DB layer — caught at next spawn instead (W3 fail-closed). Acceptable because: (a) cycle-3 evidence shows schema-layer enforcement costs more complexity than it buys; (b) W3 is the practical enforcement point operators see; (c) cycle-3 review converged on this as the simpler-correct path.
- **Fact-check:** Verified — sqlite.org/draft/lang_altertable.html (T1), Rails GitHub issue #55866 (Oct 2025) production incident.
- **Status:** Open

### [M2] Post-transaction FS-writes-with-recovery-script is unreachable under the barrel migration runner

- **Raised by:** Reviewer A (#2 HIGH), Reviewer C (#4)
- **Finding:** `src/db/migrations/index.ts:100` wraps every `m.up(db)` in an outer `db.transaction(() => { m.up(db); insert_schema_version })()`. The cycle-2 design's "post-transaction FS writes happen outside the inner transaction" runs INSIDE `up()`, which is itself inside the outer transaction. Any `fs.writeFileSync` throw propagates up and rolls back the outer transaction — including the SQL changes the recovery script later expects to read from `agent_groups.workgroup_id`. The cycle-2 S7 recovery script becomes unreachable: if FS writes fail, there's nothing to recover.
- **Effort to Fix:** Medium — separate FS reconciliation from the migration runner.
- **Impact if Ignored:** High — the cycle-2 S7 resilience the design claims doesn't exist; a transient `fs.writeFileSync` failure becomes "migration appears applied but `schema_version` shows unapplied" with retry loops.
- **Suggested resolution:** **Move FS writes OUT of the migration entirely.** Approach:
  - Migration 036 does SQL-only (schema + backfill + validation). Stays inside the barrel transaction.
  - After `runMigrations` returns successfully in `src/index.ts`, a new startup phase `reconcileWorkgroupFsState()` performs the container.json `recall_scope` writes and log file outputs. Reads `agent_groups.workgroup_id` from the (now-applied) DB. Idempotent — safe to re-run.
  - If `reconcileWorkgroupFsState` throws, host startup fails loudly with operator-actionable recovery: "Migration 036 SQL succeeded; FS reconciliation failed — see logs/, fix, restart."
- **Fact-check:** Verified — `src/db/migrations/index.ts:97-103` outer transaction wrap.
- **Status:** Open

### [M3] Reconciler spawn-order race silently locks `mnemon_store_id` to wrong agent

- **Raised by:** Reviewer A (#3 HIGH), Reviewer C (#2)
- **Finding:** Cycle-2 reconciliation pseudocode (Reconciliation section) creates new workgroup rows with `mnemon_store_id = agentGroup.id` (the spawning agent's id) and `ON CONFLICT DO NOTHING` to lock it in. For a sibling pair where the codex twin (empty store) spawns first after a workgroup row deletion, the workgroup is permanently pointed at the codex twin's empty store. The 43MB of accumulated facts the cycle-2 M1 fix preserves at migration time are silently bypassed when the workgroup is recreated.
- **Effort to Fix:** Low — reconciler queries the parent row by folder slug, same rule the migration applies.
- **Impact if Ignored:** High — non-obvious recall-history loss path that doesn't surface until an operator does workgroup-row deletion or similar admin action.
- **Suggested resolution:** Reconciler looks up parent agent_groups row by folder slug:
  ```typescript
  const parent = db.prepare('SELECT id FROM agent_groups WHERE folder = ? LIMIT 1').get(declared);
  const mnemonStoreId = parent?.id ?? agentGroup.id;  // fall back to self only if no parent exists
  db.prepare(`INSERT INTO workgroups (id, display_name, onecli_secrets, mnemon_store_id, created_at)
              VALUES (?, ?, '[]', ?, datetime('now'))
              ON CONFLICT(id) DO NOTHING`).run(declared, declared, mnemonStoreId);
  ```
- **Fact-check:** Verified — Reviewer A's empirical check of `mnemon store list` showed parent stores keyed on agent_groups.id.
- **Status:** Open

### [M4] Cycle-2 S4 structural test substring doesn't match the existing `tasks` query

- **Raised by:** Reviewer A (#4 HIGH)
- **Finding:** Cycle-2 S4 prescribes "`backlog_items` / `ship_log` / `tasks` queries in container MUST contain `WHERE ... agent_group_id = ?` substring." Container's only `tasks` query (`container/agent-runner/src/mcp-tools/dispatch.ts:140-162`) filters by `parent_session_id`, not `agent_group_id`. Per-table strategy table M5 already says `tasks` is filtered by `parent_agent_group_id` at projection time, NOT `agent_group_id` in-container. The cycle-2 assertion contradicts itself: test would fail CI on day one on correct code.
- **Effort to Fix:** Low — drop `tasks` from the assertion set.
- **Impact if Ignored:** Medium — test fails CI; either the test gets disabled (defeats its purpose) or someone "fixes" the existing dispatch query in a way that doesn't match the projection filter column.
- **Suggested resolution:** Scope cycle-2 S4 assertion to `{backlog_items, ship_log, agent_group_capabilities}` only. `tasks` is bounded by the projection's `parent_agent_group_id` filter, not by an in-container `WHERE agent_group_id = ?` clause.
- **Fact-check:** Verified — `dispatch.ts:140-162` filters by `parent_session_id`; `per-agent-projections.ts:149` uses `parent_agent_group_id` as the tasks filter column.
- **Status:** Open

## SHOULD-FIX Findings (cycle 3)

### [S1] No `PRAGMA foreign_key_check` after schema changes (defense in depth)

- **Raised by:** Reviewer B (MEDIUM)
- **Finding:** Best practice (Rails fix, sqlite.org §7) is to run `PRAGMA foreign_key_check` after schema-mutation migrations to confirm no orphan FKs were introduced. The cycle-2 design validates W1+W2 via app-level SELECTs but does not invoke SQLite's own integrity check.
- **Suggested resolution:** Add `db.exec('PRAGMA foreign_key_check')` after backfill validation, before `schema_version` bump. With M1's simpler-approach resolution (no table-rebuild), this is even simpler — just runs as a final assertion.
- **Status:** Open

### [S2] D7 stale decision record contradicts M8

- **Raised by:** Reviewer C (#1)
- **Finding:** `decisions.yaml` D7 still says "default flips to 'workgroup' at container-config.ts:74" — but cycle-1 review feedback led to M8 (no default flip; migration writes explicit recall_scope to paired groups). D7 is stale text that contradicts the current design.
- **Suggested resolution:** Update D7 description to "No default flip — keep getRecallScope default at 'self'; migration writes recall_scope: 'workgroup' to container.json for auto-paired members." Mirror the existing cycle-1 auto_judgments entry.
- **Status:** Open

### [S3] Schema preservation in table-rebuild is underspecified

- **Raised by:** Reviewer C (#3)
- **Finding:** Cycle-2 design's table-rebuild references "all existing columns from migration 001" — but migrations 002-035 may have added columns, triggers, indexes, FKs. The rebuild plan doesn't enumerate them via `sqlite_master` / `PRAGMA table_info` introspection.
- **Suggested resolution:** RESOLVED transitively by M1's simpler-approach (drop table-rebuild). With nullable `ADD COLUMN`, no rebuild is needed; no schema preservation concern. Marking S3 as "resolved by M1 resolution path".
- **Status:** Resolved transitively by M1
