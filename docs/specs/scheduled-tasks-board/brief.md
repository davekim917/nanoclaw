# Brief: Scheduled Tasks Board

> Generated by `/team-brief` — 2026-06-11 (rev 2 after 4-reviewer pass: CPO, architecture, security, Codex)
> Saved to: `docs/specs/scheduled-tasks-board/brief.md`

## Requirements

### Visibility

- The dashboard gains a **Scheduled** view alongside the existing spawn Kanban and Inbox views, showing every scheduled task across all agent groups and sessions the caller is authorized for (see scope constraint C7).
- For each task, the board shows: agent group (and its provider — Claude / Codex / OpenCode), destination channel + thread (or channel root), schedule (cron, rendered in the service timezone with a human-readable next-fire time), current status, full prompt, any pre-task script, per-fire overrides (quietStatus, flagIntent model/effort), and ownership (operator-created vs module-owned, with the owning module named).
- Both **recurring series** and **one-off future-dated scheduled messages** (`process_after` in the future, no recurrence) appear on the board.
- **Thread-scoped loops** (`scope:'thread'` tasks that live and die with their thread session) are visible and badged as thread-bound.
- The board supports grouping/filtering by agent group, by ownership (operator vs module-owned), and by health, plus free-text search over prompts. **Default sort surfaces unhealthy series first** — a die-off must be the first thing seen, not buried at row 28.

### Health (the reason this feature exists)

- The board computes a **derived health signal** per series. CRITICAL: the May/June 2026 die-offs left NO `failed` row — the death signature is a row stuck `pending` with `process_after` materially in the past. Health must therefore be **derived** (e.g. "overdue when `process_after` is past by more than one cron interval or N sweep cycles"), never read from row status alone. A series that has silently stopped firing must be visually unmissable.
- Fire-history states the board distinguishes (from available data, including derived checks): succeeded, failed, overdue/stalled, paused, processing, terminal (ended). **[AMENDED, operator-approved 2026-06-12]:** script-gated skips and quiet runs are merged under "completed (no chat output)" in v1 — distinguishing them needs a fire-outcome record the firing path doesn't write (C1); v2 owns that record. "Last fired at" and recent-fire outcomes are shown per series (bounded, e.g. last 5 fires — this requires a deliberate widening of the latest-row-per-series read shape, accepted and capped).
- For an unhealthy series, the board surfaces a best-effort coarse reason where cheaply available (paused, tries/backoff, stuck-pending-since-X); deep diagnosis links out to the existing session detail view.

### Management

- The operator can **edit a task's prompt, pre-task script, and schedule (cron)** from the board (the existing `updateTask` primitive in `src/modules/scheduling/db.ts` is the proven merge-in-place edit path). Cron edits validate against the same parser the firing path uses and fail closed with an actionable error.
- The operator can **switch which agent group runs a task** and **switch the destination channel**. A **move** is two host operations the board sequences: cancel the live row in the source session, then insert into the target (agent group, messaging group) session via `scheduleTask()` — which provides the fail-closed wiring validation on the insert. After a move, **exactly one live row fleet-wide** carries that series (no double-fire). Sibling note: siblings are wired to the same physical channel via their **own** messaging-group rows (same platform_id, different channel_type — e.g. `discord` vs `discord-codex`); the board must translate the destination channel_type to the target group's variant (verified against live wiring 2026-06-11).
- A move that changes the agent group MUST surface, before confirmation, the **credential-scope delta** (OneCLI secrets the task gains/loses: per-group `onecliSecrets` ∪ workgroup baseline). Cross-workgroup moves require an explicit confirm naming the boundary crossing. The moved task carries its prompt, **pre-task script**, cron, and overrides; the script will execute unattended in the target container's environment — the confirm must say so.
- Thread-scoped loops can be paused/resumed/cancelled (the existing calling-session-then-channel-root resolution) but are **not movable in v1** — their lifecycle is intentionally bound to their thread.
- The operator can **pause/resume** (existing `status='paused'` ↔ `'pending'` primitives — persisted, restart-survivable). **Resume after a missed slot recomputes `process_after` to the next cron occurrence (skip, don't replay)** — consistent with the scheduler's established missed-fire semantics.
- The operator can **run now**: defined as early execution of the existing pending row (`process_after` set to now; fires within one sweep cycle ~60s). If the row is already due or processing, run-now is a no-op with a clear message. Recurrence advances normally on completion.
- The operator can **delete/cancel** a series. A board-cancelled series must be distinguishable in history from a naturally-completed one (today `cancelTask` marks rows `completed` — design must pick a mechanism that preserves the distinction without changing what the firing path reads).
- Module-owned tasks are visible, badged with their owning module, and editable — every edit passes an explicit confirm step. Warning copy must be accurate: the edit **persists** until the owning module's enable/bootstrap script is re-run (e.g. `bulk-enable-memory.ts`), at which point the module's hardcoded definition overwrites it with no notice to the board; the board cannot detect that out-of-band overwrite.

### Mutation safety

- All board mutations pass an **explicit per-handler authorization gate** (the `canSteer` precedent — `requireAuth`'s read-scope filter alone does NOT authorize mutation). v1 contract: **all Scheduled-board mutations require owner or global-admin**; scoped admins get read-only within their groups. (Editing prompts/scripts is remote control of unattended agent execution — strictest tier until a need to loosen appears.)
- Board mutations record minimal provenance — `{action, actor, timestamp, before/after}` for prompt/script/cron/group/channel changes — so a misbehaving series is traceable to its last edit. **[AMENDED, operator-approved 2026-06-12]:** provenance is a single minimal `scheduled_audit` table (hashed bodies, 512-char previews, 90d prune) — the originally-assumed content-stamp is mechanically impossible (`updateTask` whitelists prompt/script only). "Full audit system" (UI, retention machinery, compliance) remains out of scope.
- All mutations go through host-side APIs (the host is the sole writer of session inbound DBs); the board never opens session DBs from the browser.

## Constraints

- [HARD] Scheduled work remains stored where it lives today, in per-session `inbound.db` `messages_in` rows (recurring rows carry `recurrence`; one-offs carry a future `process_after` with `recurrence IS NULL`). The board manages them in place via host APIs. No changes to the firing mechanism (host-sweep wake, container pickup, recurrence advance, status values the firing path reads).
- [HARD] Moves are cancel-in-source + `scheduleTask()`-into-target, sequenced by the board's host API. `scheduleTask()` provides fail-closed wiring validation on the insert (destination required; `messaging_group_agents` enforced; session resolved by agent_group + messaging_group). "Series identity" across a move is nominal (shared `series_id` string in two DBs), not a transferred row; fire history before the move stays in the source session.
- [HARD] The host process is the only writer of session inbound DBs — all board mutations execute in the host process (dashboard API routes), never out-of-process.
- [HARD] Reuse the existing BoardShell dashboard frame, auth, and API router — the Scheduled view is a third view, not a new app. Every mutation handler adds its own authorization gate per the Mutation safety requirements.
- [HARD] The Scheduled read API applies the same per-group scope filter as the existing tasks/sessions APIs (disclose-as-not-found). "Fleet-wide" means all groups the caller is authorized for (owner/`no_filter` sees all) — not a scope bypass. Prompt/script bodies return verbatim within that scope; no extra redaction in v1.
- [SOFT] Read-side current-state joins follow the shape proven in `scripts/list-scheduled-tasks.ts` (latest-row-per-series + central-DB join), extended to include one-offs; fire history is an additional, deliberately-widened, capped query.
- [SOFT] Cron schedules are interpreted in the service's timezone (`TZ` from the systemd unit); display both UTC and service-local next-fire times.
- [SOFT] Prompt/script edits enforce a sane length bound (the steer path's 4000-char precedent is the reference point, adjusted as design sees fit).

## Non-Goals (Explicitly Out of Scope)

- **Central scheduled_tasks table migration.** Known wart, deliberately deferred — rearchitecting storage is low-value churn for this feature. (Operator's instinct that session-level storage "doesn't quite make sense" is recorded — deferred, not dismissed.)
- **Creating new tasks from the board.** v1 creates via chat (`schedule_task` MCP); the board manages existing tasks.
- **Changing how modules seed their own tasks**, and reconciling board edits against module-hardcoded prompts (the overwrite-on-reseed behavior documented above is accepted for v1).
- **Per-fire output/transcript browsing.** Existing session/task detail views cover transcripts; the board links out.
- **Alerting/notifications on dead series.** Visibility is in scope; proactive alerts are not (tripwire pattern exists separately).
- **Moving thread-scoped loops.** Visible and pausable/cancellable only.

## Key Concepts

- **Scheduled series:** a `messages_in` row with `kind='task'` and `recurrence` (cron) set, identified across fires by `series_id`. Each fire completes the current row; the sweep inserts the next row (new id, same series_id) and clears recurrence on the completed one.
- **One-off scheduled message:** a future-dated `messages_in` row with no recurrence. Fires once.
- **Module-owned task:** a series seeded and depended on by a NanoClaw module (memory/wiki synth + lint, mnemon, support poller) rather than created by the operator in chat.
- **Move:** cancel-in-source + insert-into-target (two host ops, sequenced atomically by the board API), carrying prompt, pre-task script, cron, and overrides. Series identity across the move is nominal; pre-move history remains in the source session.
- **Sibling:** an agent group in the same workgroup backed by a different provider (e.g. `main` ↔ `discord-codex`). Wired to the same physical channels via its own messaging-group rows (same platform_id, sibling channel_type variant).
- **Thread-scoped loop:** an opt-in recurring task (`scope:'thread'`) living in a per-thread session, intentionally dying with the thread.
- **Stalled/overdue (health):** derived state — the live pending row's `process_after` is past by more than one expected interval. This, not row status, is the die-off signature.
- **Naming note:** the existing `tasks` table and `/dashboard/api/tasks` route serve the *spawn-task* Kanban — an unrelated concept. This feature's entity is the **scheduled series**; API and UI naming must not collide (e.g. `/dashboard/api/scheduled`, not `/api/tasks`).

## Open Questions

- None. (Pause representation resolved: existing `status='paused'` primitives, no schema change. Sibling wiring resolved by live query 2026-06-11 — see Move requirement.)

## Success Criteria

- Opening the Scheduled view shows all active series and one-offs (snapshot at writing: 32 active series — illustrative, not an acceptance constant), each with group, channel, cron + next fire, ownership, health, prompt, and pre-script — no CLI needed.
- **Stranding test:** artificially set a test series' pending row `process_after` into the past (beyond one interval) and confirm the board flags it as stalled with no `failed` status present — the June 2026 signature must be caught.
- Editing the morning-briefing prompt from the board changes what the next fire executes (verifiable in the fire's transcript).
- Moving a task from `main` (Claude) to its Codex sibling results in the next fire running in the sibling's container and posting to the same physical channel; exactly one live row fleet-wide carries the series afterward; the move confirm displayed the credential-scope delta; moving to an unwired group/channel pair is refused with an actionable error.
- Pause stops subsequent fires; resume after a missed slot schedules the next cron occurrence (no immediate replay). Run-now fires within ~60s and no-ops with a message if the row is already due/processing. Delete ends the series and is distinguishable from natural completion in history.
- A module-owned task edit always passes the warning confirm naming the owning module and the reseed-overwrite caveat.
- Every mutation endpoint rejects a caller below the required role; mutations are stamped with provenance.
